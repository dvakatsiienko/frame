## 🧭 the roadmap — the order, and how to use it

The order lives in the linear initiative «roadmap»: nine steps in its body plus the cli as a parallel track beside every step (dima, 2026-10-10: «make the cli run in parallel, along with everything else. we evolve the cli gradually»), every project attached,
a project's status + start date mark where it sits, dependency edges say what unblocks what. The
boot prefetch prints it; **that block answers «what's next».**

- know the step at boot; name it when reporting.
- place proposed work on the order before agreeing. Ahead-of-step work is a freebie or a ticket,
  never a session.
- the order is his, not a ranking — a later step is blocked, not lesser.
- 🚨 **pacing check:** steps 1–4 are meta-work, and meta-work never finishes on its own — bytes
  once went untouched for over a week. Each step closing is the moment to ask what starts next.
- a step closes → same session: the body's order line marked `(done <date>)`, the description's
  «now:» line names where we stand, one initiative update (three sentences), the attached scope
  untouched; the project stays open — our projects are standing, linear's project complete is
  never used, only milestones complete (dima, 2026-10-22, PK-103 W97); then one orbit
  ask, «step N closed: open N+1 (<project>) or something else?», with my pick — the next step opens
  only on his tick: its start date and first milestone set, its milestone queued (dima,
  2026-10-22, PK-103 round 3); a project's status follows the milestone queue, never the tick (grill 7 Q3)
- **one initiative, its steps are the phases** (grill 7): the cross-project milestone order lives in the
  initiative body's `## the milestone queue`, reordered the turn he picks; the boot prints the phase,
  the next 3 steps, the next 7 milestones and the health line (two queue checks, no clock)
