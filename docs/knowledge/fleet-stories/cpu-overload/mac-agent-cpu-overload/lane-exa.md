# Research brief — why the Mac saturates, who solved the analogous problem, and what to do

**Bottom line.** The strongest explanation is not “14 agents are too many.” It is an *event-multiplication* problem: roughly 14 long-lived sessions repeatedly launch short-lived shells, Node/Bun helpers, Git, hooks and test-built binaries across many worktrees. Every launch and filesystem event can fan out into kernel/VFS/APFS work, file-event delivery, security assessment, watcher/indexer work and sometimes directory/account/policy lookups. Your capture is unusually suggestive: load 20–60 (peaks 126–247), 59.4% system CPU, and 23,722 opens/40,563 stats in one Go run. It is not, however, a proven causal decomposition; `ps` missing short-lived processes means its 6/14-core accounting cannot identify the missing system CPU.

The best-supported *specific* causes are: (1) the heavy test gate itself is CPU/system-call intensive; (2) recursive watcher/indexer churn is plausible and has been measured in analogous Mac workloads; (3) executable-assessment/security overhead is plausible for many fresh binaries, with measured but workload-dependent gains; (4) a bug, leak or spin in an agent/hook can dominate everything. No public source I found measures the complete chain on an M4 Pro running your exact suite, so a “surely proven” single root cause would be overclaiming.

## 1. Kernel/system CPU: the findings that carry most

1. **Security assessment can sit on the launch path, but its cost is workload-dependent.** Apple documents that Gatekeeper uses the security-assessment policy subsystem (`spctl` is its CLI), while a first-hand Nix investigation measured 0–8.6% faster real builds (mean about 4.08%), and an 87.1% synthetic worst-case improvement, when executable assessments were bypassed; the same report found roughly 15–30 ms assessment-toggle overhead and network/TLS effects. That is evidence for `syspolicyd`/Gatekeeper/XProtect/amfid as a contributor when many *new* executables are launched, not proof that it explains your 59% system CPU. [Apple TN2206 (2019-07-01)](https://developer.apple.com/library/archive/technotes/tn2206/_index.html); [Nix #3789 (2020-08-18 onward)](https://github.com/NixOS/nix/issues/3789).

2. **Endpoint Security can synchronously delay execution.** Apple distinguishes asynchronous `NOTIFY_EXEC`/`NOTIFY_FORK` from synchronous authorization events: an `AUTH_EXEC` client must answer before the operation proceeds. Apple also describes muting file-event paths to reduce performance impact. This establishes a mechanism by which EDR/antivirus/MDM clients can add work or launch latency, but Apple publishes no per-event benchmark; treat it as a hypothesis until sampled on this Mac. [Apple WWDC20, 2020-06-24](https://developer.apple.com/videos/play/wwdc2020/10159/); [Apple WWDC22, 2022-06-08](https://developer.apple.com/videos/play/wwdc2022/110345/).

3. **FSEvents/watcher churn is a credible system-CPU amplifier.** A Bazel issue reports macOS large-file-generation builds driving `fseventsd` to roughly 100–200% CPU; a recent first-hand agent/workspace report found a recursive watcher delivering per-file events under `node_modules`, `.git` and build directories, with `fseventsd` reaching about 100% CPU and 36 GB footprint. The latter fixed it by passing literal hot-directory exclusions to the OS-level FSEvents stream, dropping idle watchers and stopping teardown/re-arm churn. These are analogies, not proof of your machine’s state. [Bazel #7527 (2020-02-01 onward)](https://github.com/bazelbuild/bazel/issues/7527); [Daintree #12455 (2026-11-06)](https://github.com/daintreehq/daintree/issues/12455).

4. **APFS/VFS metadata work is real, but there is no clean Apple-silicon fork/stat benchmark matching your workload.** A Rust issue measured recursive traversal on macOS APFS at 292.6 ms versus 170.6 ms for GNU `ls` on the same tree; the difference included userspace syscall patterns, so it does not isolate APFS kernel cost. An older directory benchmark found some APFS metadata APIs substantially slower than HFS+ (for example 11.2 s versus 4.9 s in one worst case). [rust-lang/libc #2619 (2022-01-09)](https://github.com/rust-lang/libc/issues/2619); [Tempel directory benchmark (2019-04-22)](http://blog.tempel.org/2019/04/dir-read-performance.html).

5. **Process spawning itself can be pathological when an agent or hook spins.** Claude Code issue #34568 reports a macOS ARM64/Bun process whose sample was 96.9% in `__posix_spawn`, with repeated `socketpair/open/close/kevent` activity; issue #55609 reports a hook/interruption repro with 1000/1000 samples in `__posix_spawn → __socketpair → setsockopt → close`, 1.577 GB footprint growth in 10 seconds and system-wide fork failures. These are bug reports, not a statement that every normal spawn is expensive—but they make “look for a runaway child/hook” a higher priority than speculative tuning. [Claude Code #34568 (2026-03-17 issue history)](https://github.com/anthropics/claude-code/issues/34568); [Claude Code #55609 (2026-05-02)](https://github.com/anthropics/claude-code/issues/55609).

6. **The requested claims about `opendirectoryd`, `cfprefsd`, `notifyd`, sandbox and APFS clone cost remain unproven here.** I found no controlled public benchmark assigning a material fraction of a coding-agent run to `getpwuid`, preference/notify IPC, sandbox checks or APFS clone metadata. Your `top` names those daemons, but a daemon’s instantaneous `%CPU` is correlation, not attribution. This is an evidence gap, not evidence that they are harmless.

## 2. Who hit it and who solved the analogous problem

1. **A directly similar Mac agent report exists.** A first-hand Mac-mini report describes an M4 Pro/48 GB running many Claude agents, full tests consuming essentially all CPU, and load average reaching 172 when two test runs overlapped. The author’s solution was a queue, per-company CPU caps/priorities, and test-impact selection: one 13,100-test suite was split by module and one change ran about 9,100 tests. This is strikingly close to your observation that the gate—not the number of idle model sessions—is the bottleneck. [Pelton (2026-10-12)](https://www.nathanpelton.com/content/blog/ai-workflow/claude-code-agent-team-mac-mini.htm).

2. **Thirty agents on “own servers” does not mean thirty Mac-local test workloads.** The report says up to 30 Claude Code/Codex CLIs run in tmux on servers, but gives no controlled CPU/RAM/OS benchmark and does not establish that every session runs local builds/tests. It supports the architecture (remote persistent host + terminal multiplexer), not a claim that 30 equivalent local gates are feasible. [Kalmykov (2026-11-05)](https://dev.to/dev1alone/how-we-run-thirty-claude-code-and-codex-agents-on-our-own-servers-and-the-tool-is-now-open-source-5c4e).

3. **The strongest 64+ example is compute-pool scaling, not a 14-core Mac.** Adam Zieliński reports about 80 Codex sessions on a home cluster with about 80 CPU threads, 288 GB RAM and 20 TB SSD, using VMs and tmux; the post itself says CPU, memory and disk become the constraints and does not provide a controlled test-throughput benchmark. [Zieliński (2026-05-26)](https://adamadam.blog/2026/05/26/running-80-concurrent-codex-sessions/).

4. **Cursor’s hundreds of agents ran on a large Linux VM and hit disk/coordination bottlenecks.** Cursor reports hundreds of workers, a single large Linux VM, roughly 1,000 commits/hour at peak, and compilation artifacts becoming the disk hotspot; it also says 20 agents could collapse throughput to that of 1–3 because of lock contention. This answers “how do they?”: abundant compute, Linux/VM isolation, low-cost model-wait concurrency, and selective/relaxed gates—not 64 independent local full test suites on a laptop. [Cursor (2026-02-05)](https://cursor.com/blog/self-driving-codebases); [Cursor (2026-01-14)](https://cursor.com/blog/scaling-agents).

5. **The Mac-only orchestrators are process/worktree managers, not capacity multipliers.** Claude Squad documents tmux plus isolated Git workspaces; Conductor is described as Mac-only in a 2026 comparison. They solve isolation and operator UX, not kernel, disk or test-gate saturation. [Claude Squad README (retrieved 2026-11-06)](https://github.com/smtg-ai/claude-squad); [Anhaia (2026-11-05)](https://dev.to/gabrielanhaia/conductor-vs-claude-squad-vs-hermes-ide-3-worktree-managers-for-parallel-agents-4818).

## 3. Linux versus macOS and the Mac mini claim

1. **There is no apples-to-apples public benchmark of your Go/Vitest/mods suite on native macOS, Linux bare metal and an Apple-silicon Linux VM.** That absence matters: claims that Linux is categorically faster for this exact workload are not proven.

2. **The clearest measured VM difference is filesystem transport.** A 2025 React dependency benchmark on an M1 Max found native Linux Docker about 5.29 s, while ordinary Mac bind-mounted configurations were roughly 8.47–9.53 s; file synchronization, volumes and OrbStack were about 3.19–4.22 s in the reported variants. This supports “keep source/build trees inside the Linux VM or use a sync/volume mechanism,” not “Linux VM CPU is always faster.” [Mainardi (2025-01-04)](https://www.paolomainardi.com/posts/docker-performance-macos-2025/).

3. **OrbStack’s own benchmark is useful but vendor-controlled.** It reports real developer workloads on an M1 Max and emphasizes workload dependence; use it as a configuration lead, not independent proof. [OrbStack benchmarks (2023-08)](https://docs.orbstack.dev/benchmarks).

4. **A Linux VM can remove Mac indexing/security/watcher work only if the hot tree is genuinely inside the VM.** A bind-mounted Mac worktree leaves the Mac VFS/FSEvents path in the critical loop; a VM-local checkout plus explicit sync changes the experiment. This is an inference from the measured bind-mount gap and Apple’s documented event/security mechanisms, not a published measurement of your suite. [Mainardi (2025-01-04)](https://www.paolomainardi.com/posts/docker-performance-macos-2025/); [Apple WWDC22 (2022-06-08)](https://developer.apple.com/videos/play/wwdc2022/110345/).

5. **The Mac mini trend is mostly “dedicated always-on capacity,” not a demonstrated magical CPU advantage.** The closest first-hand report uses an M4 Pro/48 GB and explicitly says one Mac mini is the bottleneck; the operational solution is queueing and splitting tests. A second Mac or cheap Linux box helps only when it runs the heavy gates remotely; two machines sharing the same Mac worktree via a bind mount would not remove the Mac filesystem path. [Pelton (2026-10-12)](https://www.nathanpelton.com/content/blog/ai-workflow/claude-code-agent-team-mac-mini.htm). Prices and a controlled second-machine comparison were not found, so a price/performance recommendation would be speculation.

## 5. What would prove or disprove each suspected cause

- **Runaway Claude/hook/process leak:** during saturation, a single PID’s `sample` shows a repeated user-space loop or `__posix_spawn`; disabling hooks makes the same interrupt test clean. Disproof: no abnormal PID, no repeatable hook A/B difference, and equal child counts.
- **Security assessment:** `syspolicyd`/`amfid`/`trustd` CPU or log activity rises in lockstep with fresh-binary launches; executing the same cached binary repeatedly removes the gap. Disproof: identical wall/user/sys time and daemon activity for fresh versus cached binaries.
- **FSEvents/watchers:** `fseventsd` CPU/RSS and event/drop/rescan messages rise with worktree writes; one worktree with `node_modules`, `.git`, build and coverage excluded materially lowers system CPU. Disproof: same measurements with no watchers and with a non-indexed disposable tree.
- **Spotlight:** `mds`/`mdworker` activity and indexing status correlate with the gate; an excluded clone lowers system CPU or wall time. Disproof: no indexer activity and no A/B change.
- **APFS/VFS metadata:** `fs_usage`/sample shows the gate dominated by repeated lookup/stat/open and a VM-local Linux checkout materially lowers system time while preserving the same tests. Disproof: same system CPU and syscall rate, pointing back to userland tests or security clients.
- **Directory/account/preferences IPC:** a controlled helper benchmark that performs `getpwuid`, preference reads and notifications in isolation shows the same scaling and daemon CPU. Disproof: no daemon activity and no change when those calls are removed/cached.
- **Pure test CPU/oversubscription:** one gate alone saturates all cores with low daemon CPU and near-100% user CPU; reducing internal test parallelism improves wall time without changing system time. Your observed 52–59% system time currently argues against treating this as the whole explanation.

This matrix is an inference-driven proposal, not a published benchmark.

## Verdict

The defensible verdict today is: **the Mac is saturated by the combination of a system-call/event-heavy gate and parallel agent orchestration; the dominant system-CPU source is not yet proven.** The fastest route to a solution is not “accept fewer agents”: keep 14 model sessions, but make local sessions mostly edit/plan, run only one measured gate at a time, remove avoidable spawn chains, exclude or correctly configure hot directories, and offload full gates to a VM-local/remote Linux worker. The public 30–80-agent examples succeed by supplying a much larger compute pool and by separating model-session concurrency from local build/test concurrency; the closest M4 Pro report solved the same class of failure with queueing, caps and test-impact selection—not by making one 14-core Mac execute more simultaneous gates.
