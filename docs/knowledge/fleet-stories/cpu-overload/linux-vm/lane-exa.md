# Research brief — FRM-536 (2026-11-09)

## 1. Prior art and measured results
The supplied Lima/VZ result—Go: 235–242 CPU-s versus 74–85 CPU-s in Linux, and `git --version`: 5.2 ms versus 0.5 ms—is a strong workload-specific win; it is not evidence that every workload wins (the supplied Vitest result did not). A public same-hardware fork/exec comparison is older and not Apple Silicon: 500 shells took 2.08–2.55 s on Intel macOS versus 0.38–0.44 s on Ubuntu; 100 `git status` calls took about 5.3 s versus 0.53–0.64 s ([process-startup benchmark, 2020-12-18](https://thorstenball.com/benchmarking-process-startup-time/)).

Lima issue #3814 is useful caution: on an M-series Mac, pure Go cosine work was essentially native (17.0 ms macOS, 17.6 ms VM), while a questionable `sysbench` run made Linux look catastrophically slow; the author later identified the synthetic benchmark as misleading ([Lima, 2025-08-10](https://github.com/lima-vm/lima/issues/3814)). OrbStack, Colima, Docker Desktop and Apple Container have published container/I/O comparisons, but not a directly comparable Go child-process suite; Apple Container’s per-container VM and missing builder networking are reported limitations ([runtime benchmark, 2026-04-20](https://github.com/zot24/macos-container-benchmarks)). **Flag: published fork/exec numbers on identical Apple Silicon hardware remain scarce; most claims are unmeasured for this workload.**

## 2. Distro
Use a stock Ubuntu/Debian arm64 cloud image as the control: compatibility and glibc matter more than shaving image size. Alpine is not the default recommendation for this suite: an Alpine-user report measured Python compilation 66% slower than Debian and attributes plausible losses to musl allocation/string and pthread-lock behaviour ([Alpine discussion, 2022-06-21](https://lists.alpinelinux.org/~alpine/users/%3C6df8863e77b970b466dbfc9a3a5c2bcec3199f48.camel%40aquilenet.fr%3E)); that is not a Go fork benchmark, so treat it as a warning, not proof.

After first boot, measure `systemd-analyze blame`, then disable only nonessential timers/services: `snapd` if nothing uses snaps, `apt-daily*`/unattended upgrades during the gate, cloud-init after provisioning, multipathd when there is no multipath storage, and MOTD/news. Ubuntu documents unattended-upgrades as a security default and the supported way to disable it ([Ubuntu, 2023-11-21](https://ubuntu.com/blog/ubuntu-updates-best-practices-for-updating-your-instance)); systemd explicitly warns that `blame` is not a complete latency measure ([systemd, accessed 2026-11-09](https://freedesktop.org/software/systemd/man/latest/systemd-analyze.html)). **Flag: the exact CPU cost of each service on this VM is unmeasured; do not cargo-cult-disable security updates on a long-lived exposed VM.**

## 3. Lima/VZ settings
Start with VZ, arm64 guest, Rosetta off, 6–8 vCPUs and 8 GiB; test 4/6/8/10 vCPUs rather than assuming “more is faster.” Lima exposes CPU, memory, nested-virt, Rosetta, mount type and VM type as explicit settings ([Lima create reference, 2026-02-21](https://lima-vm.io/docs/reference/limactl_create/)); VZ is Apple’s native virtualization path and requires macOS 13+ ([Lima VZ docs, 2026-02-21](https://lima-vm.io/docs/config/vmtype/vz/)). Oversizing vCPUs can steal scheduling capacity from the other AI sessions; pinning/host CPU behaviour is not published for this exact Mac.

Keep the source, Go caches, temporary test output and disposable databases on the VM’s local disk; use tmpfs only for genuinely disposable high-churn paths (`/tmp`, selected test data), not an unbounded Go cache. Do not count on memory ballooning to make an 8–16 GiB allocation harmless: Lima currently reports no practical VZ ballooning support ([Lima issue #4220, 2025-10-19](https://github.com/lima-vm/lima/issues/4220)). QEMU is a comparison fallback, not the first choice. **Flag: disk-cache options and tmpfs gains need measurement on this suite; Tart’s published Xcode result actually remained slower than host (2:19 versus 3:14–3:59) despite cache options ([Tart benchmark, 2025-03-23](https://github.com/openai/tart/blob/main/benchmark/README.md)).**

## 4. Code transfer and correctness
For a commit gate, the best invariant is: resolve the commit on the host, push it to a bare repository in the VM, and create/reset a guest-side worktree at that commit. This avoids macOS filesystem semantics and makes the tested tree exactly identifiable; the cost is transferring changed objects and checkout work.

For an interactive loop, rsync over SSH to the VM disk is the robust baseline; use `--delete` plus explicit exclusions and record the commit SHA. A live VZ virtiofs mount is convenient but should not hold build caches or `.git`: Lima documents virtiofs for VZ and warns that reverse-SSHFS caching can show stale host data ([Lima mounts, 2026-07-07](https://lima-vm.io/docs/config/mount/)). A real-world workspace tool reports rsync copy mode, live virtiofs mode, and a concrete failure where guest `git worktree` writes guest absolute paths into a shared `.git/config` ([coop workspaces, accessed 2026-11-09](https://github.com/trailofbits/coop/blob/main/docs/workspaces.md)). **Flag: mutagen and overlayfs numbers were not found; treat them as candidates for a small local benchmark, not established wins.**

## 5. Keeping it warm
Keep one persistent, plain Lima instance running; boot cost then disappears from each test. Provision once, snapshot/recreate from a known image periodically, and run a health check (`uname`, kernel, Go/Node versions, free space, clock, git SHA) before use. Persist `GOCACHE` and `GOMODCACHE` on the VM disk, keyed or invalidated by Go version, architecture, `go.mod`/`go.sum`, and relevant build flags. Go documents both cache locations and says the build cache is safe for concurrent invocations ([Go command documentation, 2026-10-20](https://pkg.go.dev/cmd/go)).

Match host and guest toolchain versions explicitly; do not assume host-built binaries are valid guest artifacts. Keep the VM’s package update job manual or scheduled outside gates, and periodically rebuild rather than mutating indefinitely. **Flag: public Lima boot-time and multi-week-health numbers were not found.**

## 6. Complementary tools
The highest-confidence additions are not exotic: native arm64 Go and Node versions; a recent Git built for arm64; persistent Go caches; `rsync`; `fio`, `hyperfine`, `perf`/`strace` for diagnosis; and a minimal systemd service or SSH command that launches tests without a login shell. Set the Linux CPU governor to `performance` only during controlled benchmark runs if the guest exposes CPUFreq; Linux documents that it requests the highest permitted frequency ([Linux kernel CPUFreq, accessed 2026-11-09](https://docs.kernel.org/admin-guide/pm/cpufreq.html)). Do not assume it changes Apple’s host frequency policy. `GOFLAGS` should encode only stable project policy; never globally add `-count=1` when measuring warm-cache throughput.

## 7. Measuring a clean win
Measure two products separately: **end-to-end gate** = sync/commit verification + guest test + result retrieval; **steady-state runner** = test only after the VM and caches are warm. Record wall, user, sys CPU, peak RSS, VM memory pressure, test count, cache hit state, commit SHA, tool versions, vCPU/RAM, and host thermal/load state. Use ≥10 repetitions, discard a warm-up only when explicitly labelled, and report median/p95—not one run; a current container benchmark follows this pattern (four runs × three iterations, same machine, cache clearing and outlier rules) ([benchmark methodology, 2026-04-20](https://github.com/zot24/macos-container-benchmarks)).

Alternate arms in randomized order, cool the Mac, keep other AI sessions fixed, separate cold/warm page-cache cases, and include sync. Avoid host-mounted source/cache directories in the Linux arm. `go test -count=1` is appropriate for a cold/uncached test measurement, but changes the question; default Go caching is part of the real developer workload.

## What we’d borrow first
1. **Persistent arm64 Lima VZ guest, 6–8 vCPUs/8 GiB, Rosetta disabled**, with a 4/6/8/10-vCPU sweep ([Lima settings](https://lima-vm.io/docs/reference/limactl_create/)).
2. **Guest-local checkout and caches**; use rsync for iteration and bare-repo/worktree-at-SHA for commit gates ([coop workspace transport](https://github.com/trailofbits/coop/blob/main/docs/workspaces.md)).
3. **Persistent `GOCACHE` + `GOMODCACHE`**, versioned by toolchain and dependency state ([Go cache documentation](https://pkg.go.dev/cmd/go)).
4. **Virtiofs only for convenience, never for hot test I/O; local disk/tmpfs for churn**, because Lima documents the transport trade-off ([Lima mounts](https://lima-vm.io/docs/config/mount/)).
5. **A benchmark harness that times sync + test, separates cold/warm, and reports p95 under controlled thermal/load state**, following reproducible-runtime methodology ([benchmark methodology](https://github.com/zot24/macos-container-benchmarks)).
