The supplied measurements point to a workload-specific choice: keep the Linux VM for the subprocess-heavy Go suite, but not for Vitest, which showed no CPU gain. Public comparisons do not establish that every test suite—or every Apple Silicon VM—will be faster.

### 1. Prior art and where it breaks
On an M3 Mac, a Linux kernel compile took 2:22 in Lima, 2:18 in OrbStack, 2:25 in UTM/Apple Virtualization and 2:41 in UTM/QEMU; these are compile results, not Go subprocess tests. A 2017 process-launch study reported Linux about 10× faster than macOS, while newer spawnbench results show that fork cost depends on heap shape; neither is a same-Mac Apple Silicon comparison of this Go suite. Sources: “UTM vs OrbStack vs Lima” (3 May 2026); “Benchmarking OS primitives” (3 June 2017); spawnbench (undated).
Apple `container` uses a VM per container and depends on macOS 26 for its full experience; reported failures include 3–10× slower filesystem throughput than Docker/Multipass. Tart is used for CI, but a user reported a build rising from ~10 to ~80 minutes after switching from a shared directory to a disk—the cause and generality were not established. Sources: Apple `container` technical overview (current); Apple Container benchmark (27 June 2026); Apple issue #948 (10 December 2025); Tart issue #1161 (6 November 2025). Colima, OrbStack and Docker Desktop comparisons mostly measure container or mounted-file performance, not this VM-local Go workload.

### 2. Distro and background work
A published Ubuntu 24.04 minimal ARM64 cloud-image manifest includes `snapd` and `unattended-upgrades`; that does not establish what your Ubuntu 26.04 image contains. Ubuntu documents daily unattended-upgrade timers. After first-boot provisioning, disable or control scheduled updates for benchmark predictability; disable `multipathd` only if present and multipath storage is unused, and disable cloud-init only after provisioning. Sources: Ubuntu 24.04 minimal cloud-image manifest (current); Ubuntu automatic-updates documentation (15 July 2026); cloud-init disable documentation (current); Ubuntu multipath documentation (26 June 2026).
Ubuntu/Debian glibc is the safer compatibility baseline. Alpine is small and uses musl, but no retrieved evidence shows it improves this Go suite; an older libc comparison measured faster dynamic self-exec for musl, not a distro-level Go test win. Sources: Alpine cloud images (3 November 2026); “Comparison of C/POSIX standard library implementations” (14 September 2018).

### 3. Lima/VZ settings
Use native arm64 with `vmType: vz`; keep Rosetta and nested virtualization off unless a test needs them. Lima documents VZ as its macOS default, and its nested-virtualization setting is for running another VM inside the guest. Start by comparing 6/8/10 vCPUs and 8/12 GiB, tracking host responsiveness, guest swap and test wall time: the current 10-vCPU/8-GiB setup is a reasonable baseline, not a proven optimum. Avoid simply assigning all host capacity; overcommit can hurt performance. VZ memory ballooning was merged with configurable minimum/idle targets, but its benefit for this workload is unmeasured. Sources: Lima VZ docs (2 November 2026); Lima ballooning PR (updated 31 July 2026); Red Hat VM CPU guidance (24 September 2026).
Keep source, Go caches and `/tmp` work on the guest disk, not a live host mount. Test tmpfs for `/tmp` only if its peak use fits comfortably in guest memory; tmpfs trades disk I/O for RAM pressure. Lima supports VZ/virtiofs for sharing, but that does not make a shared tree equivalent to guest-local storage. Sources: Lima mount docs (6 November 2026); Linux tmpfs docs (18 October 2026).

### 4. Getting code in correctly
Best commit gate: push commits to a bare repository in the VM, then create/reuse a guest-local worktree at the exact commit SHA. Git worktrees check out a specified commit and share repository objects; this avoids treating a mutable host directory as the test artifact. Rsync and Mutagen are reasonable incremental developer-sync options, but they do not by themselves prove the tested tree equals a commit. Lima supports virtiofs on VZ; use a read-only mount plus guest-local overlay only if hashes and semantics are verified. A separate directory-sharing benchmark measured first syncs around 1.6–1.9 s and one mount/cache sync at 2.9 s with virtiofs versus 29.5 s with 9p; this was not a comparison of all the proposed methods or your workload. Sources: Git worktree docs (5 October 2026); Mutagen synchronization docs (undated); Lima mount docs (6 November 2026); directory-sharing benchmark (undated).

### 5. Keeping it warm
Prefer a persistent instance: Lima 2.2 supports automatic startup and keep-alive. Persist guest-local `GOCACHE` and `GOMODCACHE`; keep Go and Node versions pinned to the host project’s versions, while keeping Linux and macOS caches separate. I found no directly comparable Lima 2.2 boot-to-ready measurement for this use case, so count startup separately rather than assuming it is negligible. Sources: Lima autostart docs (12 September 2026); Go command docs (20 October 2026); Go installation docs (current).

### 6. Tools and tuning inside the guest
There is no evidence here that rebuilding Git with special flags improves this suite; use native ARM64 Git and benchmark the actual commands. Keep Go’s build cache warm, and measure rather than blindly raising package/test parallelism. A performance CPU governor is worth trying only if the guest exposes CPUFreq; Apple Silicon guest behavior and gains were not measured. Use tmpfs selectively for short-lived `/tmp` data; retain the normal init and remove unnecessary boot services rather than replacing it. Sources: Git performance benchmark tool (undated); Go command docs (20 October 2026); Ubuntu CPU performance docs (26 June 2026); Linux tmpfs docs (18 October 2026).

### 7. A clean A/B
Time both **sync + test** and their components. Pin the same commit, toolchain, flags and test inputs; use `-count=1` when you need to defeat Go’s successful-test-result cache, and report build-cache-cold and build-cache-warm runs separately. Alternate host/VM order, repeat runs, report medians and ranges, keep the Mac plugged in and otherwise quiet, and distinguish warm from cold page-cache results. Record wall, user and sys time. Sources: Go command docs (20 October 2026); Go performance-monitoring guidance (undated); Apple Container benchmark methodology (27 June 2026); M3 VM comparison setup (3 May 2026).

### What we’d borrow — five highest-value choices
1. **Persistent, native-arm64 Lima/VZ guest; Rosetta off; keep test files on its own disk.** Lima VZ docs (2 November 2026); the M3 compile comparison (3 May 2026).
2. **Guest-local bare Git repo plus a worktree pinned to the commit SHA.** Git worktree docs (5 October 2026).
3. **Persistent guest-local Go module and build caches; pin toolchain versions.** Go command docs (20 October 2026); Go installation docs (current).
4. **Quiet the runner after provisioning: control apt timers; remove only confirmed-unused services.** Ubuntu automatic-updates docs (15 July 2026); cloud-image manifest (current).
5. **Benchmark a vCPU/memory sweep and selective `/tmp` tmpfs; do not assume more CPUs or a governor setting helps.** Lima config defaults (10 October 2025); Linux tmpfs docs (18 October 2026); Ubuntu CPU performance docs (26 June 2026).
