# Research brief — why Git starts cost kernel time on macOS, and how to cut it

**Scope note.** “Measured” below means a timing/counter in the cited source; “reported” means an implementation or incident report; “inference” is explicitly marked. Dates and versions are included for every external fact. The owner’s machine facts and measurements are treated as **measured — owner’s traces, 2026-11-07; Darwin 27.2.0, arm64, Homebrew Git**.

## 1. Locale: the strongest confirmed lead

- **Measured:** setting `LANG` reduced 500 `git --version` launches from 4.34 s to 2.62 s, and `LC_ALL=C` to 2.41 s; the suite used 13% less CPU and 16% less wall time. The trace changed `cfprefsd` 3.56→0.00 CPU-s, `opendirectoryd` 2.27→0.01, `notifyd` 1.60→0.13, Git 36.2→24.9 CPU-s, and p50 launch 9→6 ms — **owner’s measurement, 2026-11-07; Homebrew Git, Darwin 27.2.0**.
- **Reported:** GNU `libintl` locale discovery can call CoreFoundation, including `CFLocaleCopyCurrent`, and thereby libdispatch — **GNU gettext bug #43404, 2018-09-16; gettext bug report, OS version unstated** ([source](https://lists.libreplanet.org/archive/html/bug-gettext/2018-09/msg00019.html)).
- **Reported/measured:** with locale variables absent, a current gnulib/gettext path called `CFLocaleCopyPreferredLanguages` 5,004 times during 5,000 locale restores; 24 crash reports implicated CoreFoundation state after `fork`; a cache patch produced zero crashes in 600 runs — **bug-gnulib report, 2026-11-04; macOS 27.2 build 26B123, M3 Max, gettext 1.0/0.21.1** ([source](https://lists.endsoftwarepatents.org/archive/html/bug-gnulib/2026-11/msg00035.html)). This strongly confirms the mechanism, but is not an independent 1.7× benchmark.
- **Reported:** a separate benchmark measured 100 clean-repository `git status` calls at 5.21–5.38 s on macOS Catalina 10.15.7 versus 0.53–0.64 s on Ubuntu 20.10; trivial native launches were 0.21–0.24 s versus 0.01–0.02 s — **Thorsten Ball, 2020-12-14; Git repository main commit `62cc96c`, Catalina 10.15.7/Ubuntu 20.10** ([source](https://thorstenball.com/benchmarking-process-startup-time/)). It does not isolate locale.
- **Reported:** `LC_ALL=C` forces untranslated English output; a macOS 13/Darwin 21.6.0 arm64 reproduction showed translated “Formulário especial” becoming “Special Form” — **gettext report, 2024-11-30; Homebrew libintl 0x001605** ([source](https://lists.libreplanet.org/archive/html/bug-gettext/2024-11/msg00049.html)). **Inference:** safe for Git automation that consumes English output, but it breaks localized messages and may affect scripts/users expecting translated diagnostics. Prefer `LANG=C.UTF-8` or `LC_ALL=C` only in the agent’s Git environment, then test hooks.

## 2. Cheap Git work beyond locale

- **Reported:** Git reads system, global, XDG and repository configuration by default; `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_COUNT`, `GIT_DIR` and explicit `-c` control that work — **Git documentation, 2026-11-07; current Git docs** ([source](https://git-scm.com/docs/git-config)). No published per-start number was found. **Inference:** in a hermetic fixture, set `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `HOME` to a minimal directory, and `GIT_DIR` explicitly; this can remove preference/config and discovery noise, but cannot explain the owner’s dominant Sandbox samples by itself.
- **Reported:** `NO_GETTEXT` builds Git English-only and avoids the gettext dependency; MacPorts specifically recommended disabling NLS/CFPreferences/CFLocale integration for `fork`/`exec` workloads — **Git INSTALL at commit `c4d2539`, accessed 2026-11-07; Git source; and MacPorts ticket #49421, 2015-10-24; gettext 0.19.5.1/GNU make 4.1** ([INSTALL](https://github.com/git/git/blob/c4d2539af751ed394ee68c02fe688e75c647c5fe/INSTALL), [MacPorts](https://trac.macports.org/ticket/49421)). No controlled startup gain was published. **Inference:** a custom `NO_GETTEXT` Git is worth A/B testing, but a static build or fewer dylibs is not proven to beat the already observed environment fix.
- **Reported:** `core.untrackedCache` avoids repeated untracked-directory scans; `core.splitIndex` reduces index rewrites; `feature.manyFiles` bundles `index.skipHash`, index v4 and untracked cache — **gitperf configuration playbook, accessed 2026-11-07; Git feature behavior current at retrieval** ([source](https://gitperf.com/chapter-21.html)). These optimize status/index work, not process creation. `core.fsmonitor=true` starts one long-lived per-worktree daemon using filesystem notifications and IPC — **Git 2.55.0 documentation, 2026-11-07; feature history 2.36.0** ([source](https://git-scm.com/docs/git-fsmonitor--daemon)).

## 3. macOS process-start cost

- **Measured:** Crashpad’s double-fork launcher took >622 ms on macOS 11; the first fork was ~359 ms and nested fork ~263 ms; replacing nested fork+exec with `posix_spawn` reduced it to 257 ms (~59%) — **Crashpad change, accessed 2026-11-07; macOS 11 Big Sur, Intel i5-1038NG7** ([source](https://chromium.googlesource.com/crashpad/crashpad/+/1c37daa5acd500633cdffc7f6db61d8c6b32b771)). This is not an Apple-silicon floor, but proves fork can dominate.
- **Measured:** a third-party Darwin benchmark on M3 Max/Go 1.26 reports `os/exec` 2.469 ms versus posix_spawn-based `fastexec` 1.397 ms sequential (1.8×), and 485 µs versus 149 µs parallel (3.3×); with a touched 4-GiB parent, `os/exec` worsened 12% while the spawn path stayed ~1.46 ms — **fastexec benchmark, 2026; Go 1.26, Darwin arm64** ([source](https://pkg.go.dev/github.com/zchee/fastexec)). Treat as one implementation’s benchmark, not a universal floor.
- **Reported:** Go’s `os/exec` uses fork/exec on Darwin; Chromium’s production launcher uses `posix_spawnp` — **Go source/test documentation, accessed 2026-11-07; current Go; and Chromium source, accessed 2026-11-07; Chromium main** ([Go](https://go.dev/src/os/exec/exec_test.go), [Chromium](https://chromium.googlesource.com/chromium/src/base/+/refs/heads/main/process/launch_mac.cc)).
- **Reported:** dyld parses dependencies, maps dylibs, binds symbols, fixes images and runs initializers; page-in linking and cached launch work reduce repeated work — **Apple WWDC22, 2022-06-08; macOS-era dyld** ([source](https://developer.apple.com/videos/play/wwdc2022/110362/)).
- **Measured:** first-run executable assessment was ~180 ms cold/~120 ms warm with XProtect enabled versus ~9/~3 ms disabled on an M2; subsequent launches were ~8/~4 ms enabled — **Cargo PR #15908, accessed 2026-11-07; Rust/Cargo development, M2 macOS** ([source](https://github.com/rust-lang/cargo/pull/15908)). **Inference:** Gatekeeper/XProtect matters mainly for new/uncached executables; the owner’s repeated Git path and trace attribution point more strongly to Sandbox and locale than to first-run policy scans.
- **Reported:** a sandboxed parent’s directly launched helper inherits its sandbox capabilities; Apple documents checking entitlements with `codesign --entitlements` or Activity Monitor’s Sandbox column — **Apple App Sandbox documentation, accessed 2026-11-07; App Sandbox docs** ([source](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html)). **Inference:** the Claude parent’s profile can therefore tax every child open; identify the parent PID, inspect `codesign --entitlements :- <parent>`, Activity Monitor’s Sandbox column, and compare a child launched from an unsandboxed terminal. A private SBPL profile dump is not documented as a stable supported API.
- No opened source supplied a universal Apple-silicon `fork`/`exec` floor, a same-hardware Linux comparison, or evidence that macOS 26 or 27 raised that floor. The owner’s 27.2 Sandbox stack is therefore the best machine-specific evidence.

## 4. Similar cases and no-process designs

- **Measured:** Bazel on macOS reported 659.272 s sandboxed versus 312.721 s local (~2.11×), execution 653.128 versus 307.026 s — **Bazel issue #2424, 2017-01-25; Bazel 0.5-era discussion** ([source](https://github.com/bazelbuild/bazel/issues/2424)). Another LLVM target measured 38.560 s local, 41.092 s Darwin sandbox, 53.806 s copy sandbox — **Bazel issue #8230, 2019; macOS** ([source](https://github.com/bazelbuild/bazel/issues/8230)). This supports reducing sandboxed filesystem setup, not disabling security blindly.
- **Measured:** persistent `git cat-file --batch` made StGit uncommit/rebase of 1,470 Linux-kernel patches 6–8% faster — **Git mailing list, 2008-08-10; cat-file batch around Git 1.5.6-rc0** ([source](http://public-inbox.org/git/20080810235845.GA5106@diana.vm.bytemark.co.uk)). Current docs confirm batch modes keep one Git process alive — **Git 2.55/2.56 docs, 2026-11-07** ([source](https://git-scm.com/docs/git-cat-file)).
- **Measured:** gitoxide checkout of Linux v5.16 on macOS 12/APFS took 3.303 s versus Git 4.622 s at 10 cores; one core 6.820 versus 7.911 s — **gitoxide discussion #349, 2022-03-10; macOS 12, APFS/SSD** ([source](https://github.com/GitoxideLabs/gitoxide/discussions/349)). It did less work (notably index writing), so it is not a startup/status promise.
- **Reported:** go-git is pure Go and can eliminate fork/exec, but explicitly warns compatibility with reference Git is difficult — **go-git README, accessed 2026-11-07; v6 development line** ([source](https://github.com/go-git/go-git/blob/main/README.md)). Git filters/hooks make replacement risky: git-crypt’s documented model excludes filenames and metadata, and its issue reports one `git check-attr` process per file can dominate large repositories — **git-crypt 0.8.0 README, 2025-09-23; issue update 2024-12-18** ([source](https://github.com/AGWA/git-crypt/issues/45)).

## Ranked five cheapest experiments

1. **Set locale in the agent environment.** Command: `env LANG=C.UTF-8 LC_ALL=C git --version` and rerun the 500-launch and full suite A/B. **Expected:** already measured 1.7× launch improvement, 13% suite CPU reduction; highest-confidence gain.
2. **Eliminate config/discovery noise.** Command: `env LANG=C.UTF-8 GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null HOME=$(mktemp -d) git --git-dir="$PWD/.git" status`. **Expected:** unknown; kill it if `dtruss`/Trace2 and wall time do not move.
3. **Replace Go fork/exec with Darwin `posix_spawn`.** Command: benchmark the fixture binary with `GODEBUG=execwait=2` and a small `posix_spawn` wrapper (or `fastexec`) against `go test -count=20`. **Expected:** third-party M3 result 1.8× sequential/3.3× parallel; owner-specific gain is inference and must be measured.
4. **Prove/disprove inherited Sandbox cost.** Command: run `sudo dtruss -f -t open,execve,stat64 go-test-binary` once from Claude and once from Terminal, while recording `sample`/`spindump` and `codesign --entitlements :- <parent>`. **Expected:** if Sandbox samples fall materially, move the heavy fixture runner outside the sandbox or use a narrow helper; otherwise stop pursuing it.
5. **Amortize Git processes.** Command: change the hottest object-query loop to one `git cat-file --batch-command` process and benchmark `hyperfine --warmup 3 'old' 'new'`. **Expected:** at least the published 6–8% workload gain; potentially larger here because the owner measured ~660 processes/s, but that larger number is inference.

## Looked for but did not find

No opened source gave a controlled 1.7× locale benchmark independent of the owner; a universal Apple-silicon/macOS-version process-start floor; a same-M4-Pro Linux comparison; proof that macOS 26/27 raised the floor; a published per-start gain for `GIT_CONFIG_NOSYSTEM`, `includeIf`, `core.untrackedCache`, split index, `feature.manyFiles`, or a static/no-gettext Homebrew Git; or a correctness-preserving full replacement for Git when hooks, attributes, submodules, and git-crypt filters are active. The earlier Claude idle/Desktop, Developer Tools exemption, WindowServer, and Mac mini findings were not repeated, as requested.
