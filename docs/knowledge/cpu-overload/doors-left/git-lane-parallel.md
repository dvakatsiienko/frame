## Bottom line

For this workload, the measured custom minimal Git remains the strongest evidence-backed choice: **3.4 ms per start and a 16% whole-suite improvement** in the figures stated in the question. I found no published, like-for-like benchmark on Apple silicon/macOS 27 that beats it while also exercising real child processes, hooks, signed commits, and git-crypt clean/smudge filters. There are useful alternatives for narrower parts of the work, but none is a demonstrated drop-in replacement for that exact test mix.

Project identifiers below are included verbatim. The benchmark figures are labeled with who measured them and the platform when those details were available.

## 1. Projects that could reduce Git process cost or replace Git operations

- **Grit (`gitbutlerapp/grit`) — the most promising in-process candidate, with important helper-process caveats.** It is a maintained Rust Git engine and linkable `grit-lib`, with a CLI for macOS and Linux. The public snapshot reports **584 GitHub stars as of Nov. 6, 2026**; the latest release found was **v0.5.30, Nov. 6, 2026**. Grit’s library supports hooks, clean/smudge filters, credential helpers, and signing helpers, but its documented command runner spawns operating-system processes to run those helpers. Thus it can avoid launching Git for core repository operations, but does **not** eliminate all process launches in the workflow you described.
  - **Published numbers:** Grit’s own benchmark suite compares against Git 2.43 on a 4-vCPU Intel Xeon Linux VM, not a Mac. In one 10,000-file synthetic repository, `commit` measured about **16.8 ms for Grit vs. 27.2 ms for Git**; several operations improve, while small `status` and some other commands are comparable or slower. Those results are not a macOS process-start benchmark and do not demonstrate your exact hooks/signing/filter path.
  - **Hooks, signing, filters:** The library has explicit subprocess hooks for those integrations. The surfaced sources do not establish a git-crypt-compatible, end-to-end signed commit with the exact filters and hooks in your test suite.

- **Gitoxide (`GitoxideLabs/gitoxide`, also called `gix`) — actively maintained, but not a verified drop-in for these writes.** The latest-release information found says **12.1K stars** and a release on **Nov. 4, 2026**. It is a Rust library and CLI with object and ref writing, worktree features, and emerging commit/signature support. Current project status still marks hook discovery/execution and the clean/smudge filter base as incomplete; its filter support is not enough to establish complete Git-compatible behavior for this workload. I found **no published macOS benchmark** showing it beats your custom Git build on the relevant operations. Treat it as a fast-moving library to evaluate for selected operations, not as a full replacement for `git add`/`commit` with your semantics.

- **libgit2 (and bindings such as `git2-rs`) — viable for a bespoke embedded implementation, not a turnkey Git replacement.** libgit2 is a mature, cross-platform C library with production use in language ecosystems including Python, Perl, and Node. Its APIs provide custom in-process filter callbacks and commit-signing callbacks/signature creation. That makes it possible to implement selected writes without launching the Git executable. However, hooks and external filter programs such as git-crypt require application-owned glue and compatibility work; the evidence reviewed does not show automatic Git CLI semantics for those features. I found no current star count, latest release date, or Apple-silicon benchmark that would allow a fair speed comparison.

- **Noot and Git Twig are not process-startup replacements.** Their documented writes use the system Git CLI; their useful feature is that reads can use libgit2. The Twig description specifically says its writes go through system Git so hooks, LFS, signing, and credential helpers continue to work. That is a compatibility pattern, not a way to remove Git process launches.

- **No evidence surfaced that changes the assessment of `nit`** beyond the facts you already supplied. I did not re-evaluate it.

## 2. What high-volume users do

The most useful distinction is between **avoiding Git process startup on one machine** and **scaling Git serving or repository work across a fleet**. Most published large-scale examples address the latter, not your local `exec` cost.

- **GitHub: replace costly server-side hook startup.** GitHub reported that Ruby pre-receive hooks averaged about **880 ms**, with most time spent loading dependencies; the hooks ran as subprocesses for pushes. It rewrote them into a Go service and reported a **95% reduction in P99 hook time**. This is a concrete example of removing a heavy per-request hook runtime, but it is server-side push validation—not a macOS Git client replacement or a generic persistent Git command daemon.
- **GitLab/Gitaly: cache and reduce repository work.** GitLab recommends a reusable `pack-objects` cache for clone/fetch responses, using `fetch` rather than repeated `clone` in CI where appropriate, reducing concurrent clone bursts, and avoiding repeated `git clean` when a safe worktree can be reused. These lower server, network, and disk work; they do not establish that Git’s local command process is reused.
- **Datadog: serve CI Git traffic from a specialized cache.** Datadog says its GitRetriever synchronization fell from seconds to hundreds of milliseconds; it has served over a billion Git requests across roughly 5,500 repositories and handles over 100 million requests a week. The old backend’s fetch-serving CPU fell **3–4×**, while traffic grew about **20× in four months** and median serving latency remained around **40 ms**. This is a fetch-serving architecture, not an in-process local Git client.
- **Cursor Origin/Continuity: rebuild the server side, keep ordinary Git clients.** Cursor reports synthetic read scaling to **100 replicas**, and up to **120 pushes/second on S3 Standard** or **more than 300 pushes/second on S3 Express One Zone**, using its monorepo. Those are Cursor’s server-side stress-test figures. Agents still use the Git client; this does not reduce a local `git` process’s launch time.
- **OpenAI Pando: scale pushes and fetches without replacing the client.** OpenAI says Pando now serves its monorepo, preserves the Git protocol/client, cut median production push latency by nearly **5×**, and delivers nearly a petabyte of Git data per day. This is a server-backend result, not a local process-start result.
- **Built-in FSMonitor is a real daemon, but only for filesystem-change tracking.** Git’s `core.fsmonitor=true` starts a long-running, repository/worktree monitor on macOS and other supported platforms. GitHub’s large-worktree examples show substantial `status` improvements; for a 393,000-file Chromium worktree its table reports **5.1 s, 2.3 s, and 0.83 s** across the compared configurations. It reduces worktree scanning, not the startup cost of each Git command. It is most relevant to large worktrees, not tiny throwaway repos, and does not replace hooks, signing, or filters.
- **Long-lived `git cat-file --batch` / `--batch-command`:** This is a practical way to amortize Git startup for repeated **read-only object lookups**. One documented implementation uses an invocation-scoped batch process for immutable object queries; it invalidates cached results after mutations. It cannot replace `init`, `add`, `commit`, `worktree`, `push`, hooks, signing, or clean/smudge processing. I found no macOS benchmark for your scenario.
- **Filter-process protocol:** Git can run a configured long-running filter process to handle many files during one Git command. That amortizes filter launches **within that command**, not Git launches across commands. I found no evidence confirming that the specific git-crypt filters in your setup support this mode.
- **Generic Git command server / shared-library preload:** I found no maintained, general-purpose Git porcelain command server or widely adopted shared-library/preload scheme that replaces repeated local `git` invocations while preserving the semantics you listed. The closest well-documented command-server analogy is Mercurial’s `chg`, not Git: a reported 98-test suite with 470 Mercurial invocations took **177 s vs. 27 s on macOS** when using `chg`. That demonstrates the potential of amortizing an interpreter’s startup; it is not evidence that an equivalent Git command server exists.

For the named agent platforms, the evidence is uneven: Cursor and Codex/OpenAI have the server-side systems described above. One **nonofficial** Claude Code architecture guide claims direct `.git` metadata reads for some state checks, but I found no official benchmark validating that claim. Devin- and Conductor-specific Git process-reuse details were **not examined in sufficient detail to report a sourced implementation or number**. GitHub Actions’ published job-volume figures likewise do not establish a persistent local Git process.

## 3. Static/minimal Git and dyld on macOS 26/27

- **A fully static macOS executable is not a supported target in the Linux sense.** macOS requires dynamic system libraries, at minimum `libSystem`; third-party dependencies can be statically bundled, but the result still has a dynamic-library closure. A minimally linked Git is practical, and Git’s build system exposes options such as disabling gettext, Perl, Python, and Tcl/Tk. That fits the direction of your existing custom build; it is not a recipe for a truly static Git.
- **I found no published fully-static or minimally linked Git benchmark on Apple silicon that outperforms your 3.4 ms result.** The current Apple guidance says dyld can cache launch work in a launch closure, but the closure and remaining launch work still depend on the executable’s libraries and initializers. Apple’s page-in-linking example reports a 15 ms TextEdit launch with about 1 ms spent on fixups; that is an application example, not a Git benchmark and not proof that reducing dylib count will remove all launch time.
- **No general macOS 26 or 27 improvement to Git startup was established.** The macOS 26 report surfaced was a specific Objective-C-category/dyld launch problem in a Codex-related binary, not a general Git performance measurement. I found no public Git launch benchmark or supported user-controlled dyld-closure/prelink trick for macOS 26/27 that would overturn your direct measurements. `DYLD_PRINT_STATISTICS`/Instruments-style profiling can help identify where launch time goes, but dyld closure internals are not a substitute for a measured smaller executable.

## 4. Avoiding Git during disposable fixture setup

- **Build one canonical fixture once, then copy it per test.** A concrete CI write-up reports a fixture that previously ran **13 Git commands for each of seven repositories before each of 415 test methods**—37,765 fixed setup commands. It built immutable templates using 15 Git commands per repository and copied them for each test; across three CI shards that was 315 template commands, a **99.2% reduction** in fixed setup commands. Its post-change local setup/teardown median was **78 ms**. The reported comparison text is truncated, so I cannot give the before/after elapsed-time reduction.
- **On APFS, copy-on-write clones are a particularly good fit.** A prepared repository/worktree can be cloned at the filesystem level, avoiding Git subprocesses for the fixture copy while keeping writes private through copy-on-write. A published macOS tool description gives the example that ten 5 GB clones share roughly 5 GB until they diverge. This is a fixture-construction optimization, not a substitute for tests whose purpose is to exercise `git worktree`, hooks, signing, or filters. Ensure each test gets independent refs, index/config, hook state, and any external signing/filter resources.
- **`git fast-import` can seed many objects and commits through one process.** Git’s documentation says it writes packfiles directly and typically imports even projects with 100,000+ commits in a short time, but I found no task-matched benchmark comparing it with your fixture-building loop. It avoids one Git process per `add`/`commit` when constructing history; it does not create the normal working-tree/hook/filter execution path. It can handle existing commit-signature modes, but annotated-tag signing during import is not supported.
- **Direct object writing:** I found Git libraries with object-write APIs, but no measured, general-purpose direct-object fixture recipe for your exact combination of repository setup, worktrees, local bare pushes, hooks, signing, and git-crypt. Directly constructing objects/refs is suitable only when the test does not need to prove those Git behaviors.

## 5. Other findings and what remains unknown

- A recent macOS Git-launch measurement surfaced for a different optimization: bypassing the `/usr/bin/git` → `xcrun` shim in one Node application reduced a single `git rev-parse HEAD` spawn from **7.8–8.2 ms to 2.7–3.0 ms** on an M-series Mac; that application’s 155-test suite fell from **42.6 s to 20.7 s**. It applies only when the invocation actually takes that shim path; the measurement used Xcode Git 2.50.1 and is not comparable to your already-customized build. Check whether any test harness or wrapper is adding an `xcrun` lookup.
- Your report that the kernel accounts for about 60% of CPU is a reason not to assume every remaining millisecond is dyld: repository discovery, filesystem operations, page faults, hooks, filters, and test fixture work can all contribute. A small executable alone will not eliminate those costs.
- The headline answer is plain: **nothing in the public evidence found is a demonstrated better fit than your custom minimal build for the exact macOS 27 test workload.** Grit is worth considering if you can embed its library and validate its external-helper behavior; libgit2 is an option if you are willing to own the compatibility layer. Gitoxide is not yet evidenced as complete for the required hook/filter path.
- Not found or not established: a like-for-like macOS 27 benchmark for Grit, Gitoxide, or libgit2; verified Gitoxide end-to-end hook + signing + git-crypt support; a Git command-server or shared-library preload that handles these write operations; benchmarked direct-object fixture construction for this workload; confirmation that git-crypt supports Git’s long-running filter protocol; and sourced Devin/Conductor implementation details.
