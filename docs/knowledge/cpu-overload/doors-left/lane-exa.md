# Executive answer

Sixteen **busy** Claude Code lanes will not be made fast by changing Git alone. Your measurements say the bottleneck is principally **the test workload and macOS’s per-process/per-file security and kernel path**. The best route is a two-level design:

1. **Make each lane do far less work**: affected-test selection, shared/content-addressed results, persistent workers, and removal of avoidable child processes.
2. **Move the heavy lanes off the Mac**—preferably to Linux workers—or run only a small local admission window while keeping 16 sessions logically active.

A realistic first target is 16 sessions with **4–6 test-heavy lanes admitted at once**, not 16 simultaneous full suites. If “16 at once” means 16 agents responsive while tests queue or execute remotely, that is practical. If it means 16 local full suites at the current 240 CPU-s each, the arithmetic makes it impossible on a 14-core host without reducing work or adding compute.

## What I would do, in order

**Today (no architecture change):**

1. Add one global jobserver and start at 4 test tokens.
2. Make `GOCACHE` common and local; measure cache hits.
3. Profile the top launchers and batch/daemonize `x`, Git queries, `rg`, hooks and MCP tools.
4. Run the Vitest pool grid and the Go `-p`/`-parallel`/`GOMAXPROCS` grid.
5. Prewarm stable binaries and repeat cold/warm measurements.

**This week:**

6. Build changed-package selection with a nightly full-suite safety net.
7. Add a persistent `x` worker and an opt-in in-process harness for tests that do not require a real child.
8. Put a full repository and cache inside a Linux VM volume; do not bind-mount the hot tree.
9. Benchmark one rented ARM Linux worker. If it wins on CPU-s per suite, move test-heavy lanes there.

**Only after those tests:**

10. Try gix/go-git/libgit2 for narrowly defined read/status/object operations. Keep canonical Git for commits, hooks, signing, filters and any operation where behavioral parity matters.
11. Investigate the Sandbox/Endpoint Security client with controlled owner-approved profiling. Do not trade a speculative speedup for weakened macOS security.

## Important negative findings

I found **no published, independent apples-to-apples measurement** showing 16 Claude Code sessions with 16 concurrent full Go suites on a 14-core Apple-silicon Mac, no universal Apple-silicon fork/exec/open penalty, no credible end-to-end benchmark proving gix/go-git/libgit2 preserve all of hooks + signing + clean/smudge filters while beating your custom Git, and no reliable generic number for Claude Code’s per-hook/MCP/shell-snapshot CPU cost. Vendor claims such as “5+ agents,” “10,000 workers,” and “many agents” describe product capacity or examples—not proof that one Mac can run 16 busy lanes fast.

The key surprising door is therefore not another Git binary: **make test execution a cacheable, dependency-addressed service and treat local CPU as a scarce shared resource**. That directly attacks the 240 CPU-s suite and the 661 process/s rate, whereas moving from a 2.56-ms Git start to a faster client can only address a fraction of the total.
