# crew-designer prior research — skill practices + designer tools (parallel core ×2, 2026-09-28, ungraded)

## Recommendation
Build the skill as a small art-direction and verification workflow—not as a long list of fashionable CSS effects. The most useful pattern in the published examples is: understand the product and task, state a design direction before coding, check that the direction is specific to the brief, implement it, then inspect the rendered interface and revise it.

## 1. A practical workflow for the skill

**1. Explore the project and brief.** Inspect the existing app, stack, components, assets, and any design-system files first. Identify the user, the interface’s main job, its page type, and what real product content or evidence belongs on the screen. If the product or audience is unclear, propose a concrete interpretation and confirm it where necessary.

**2. Diverge briefly, then choose.** For open-ended work, compare two materially different directions before building. Make the alternatives differ in protagonist, layout/region roles, evidence, or interaction—not just color or decoration. Summarize each with a one-sentence rationale and a quick mobile/wide wireframe. Choose against the brief and user task; ask the user only if the alternatives would materially change the product relationship or brand position. This supports exploration without turning every implementation into an expensive variant factory.

**3. Record the chosen direction in a compact design sheet.** Include the primary task and action hierarchy; content and asset truth; mobile and wide compositions; color roles; type roles and scale; spacing, surfaces, controls, and states; one justified subject-specific signature; cliché risks; and the two most likely failure modes. Treat this as a durable specification, not an essay. Keep an existing system when present; otherwise define a small coherent token set and make the implementation consume it.

**4. Build for the product, not a genre template.** Preserve the project’s conventions. Use real or clearly marked placeholder content, task-relevant components, and functional interaction states. Do not invent metrics, testimonials, logos, certifications, screenshots, or operational data to make a screen feel credible. Make typography, palette, layout, copy, and motion reinforce the specific subject and task.

**5. Review the rendered result, fix the weakest issue, and repeat.** Render the real app; inspect screenshots at 100%; interact with important controls; and check mobile, tablet, desktop, and wide layouts. A useful default matrix is 390×844, 768×1024, 1440×900, and 1920×1080, adding 2560×1080 for full-bleed or split-screen layouts. Write findings as **observation → cause → structural fix → viewport to recheck**. Re-render after each meaningful fix. Do not claim visual verification when a browser was unavailable.

**6. Use hard gates, not a single averaged “taste” score.** A strong review asks: Is the user’s job and next action clear within seconds? Does the visual hierarchy fit the page type? Do alignment, proximity, repetition, balance, whitespace, and unity support comprehension? Does the design feel grounded in its actual domain? Does it work responsively, accessibly, and in real interaction states? The weakest critical dimension should block completion; attractive decoration cannot compensate for a broken task, fake content, or inaccessible interaction.

**Anti-generic guidance:** Tell the agent to avoid defaults when they are unearned—not to ban a style the brief explicitly requests. Anthropic’s skill calls out recurring defaults such as generic rounded-card grids, decorative gradients, identical styling across hierarchy, and certain predictable palette/layout combinations. Prefer one memorable, brief-specific device, keep supporting elements disciplined, and remove decoration that has no content or interaction job. Do not simply replace one cliché with another.

## 3. Research papers to inform the design and critique loop

- **SpecifyUI: Supporting Iterative UI Design Intent Expression through Structured Specifications and Generative AI** — arXiv:2509.07334. Encodes global layout/style and page→section→component structure in an editable specification; supports scoped edits and retrieved React exemplars. Its study supports front-loading diversity during ideation, then converging on controlled refinement; it also reports that excessive late-stage alternatives can distract from delivery.
- **Visual Prompting with Iterative Refinement for Design Critique Generation** — arXiv:2412.16829. Splits screenshot critique into text generation/filtering, region grounding, separate validation, and iterative text/box refinement; zoomed crops and coordinate cues make comments more specific and visually grounded.
- **Vision-Guided Iterative Refinement for Frontend Code Generation** — arXiv:2604.05839. Renders generated code, has a VLM critique the screenshot, translates that into code-level actions, revises, and retains the best-scoring candidate; the authors report gains of up to 17.8% after three refinement cycles on their benchmark.
- **UXBench: Measuring the Actionability of LLM-Generated UX Critiques** — arXiv:2606.16262. Makes an agent explore a running interface and collect interaction evidence before it writes a critique, then measures whether a fixed repair agent can improve the interface; useful for testing critique actionability instead of rewarding fluent but unsupported comments.
- **Do MLLMs Capture How Interfaces Guide User Behavior? A Benchmark for Multimodal UI/UX Design Understanding** — arXiv:2505.05026. Evaluates pairwise choice and explanation against real A/B-tested UI variants and expert rationales; models are near chance on choosing the behaviorally effective variant, a warning not to equate an AI judge’s aesthetic preference with user impact.
- **UICrit: Enhancing Automated Design Evaluation with a UICritique Dataset** — arXiv:2407.08850. Builds a dataset of designer critiques and UI quality ratings, then tests few-shot and visual-prompting approaches; a useful source for critique examples and region-grounded evaluation.

**A good first implementation:** combine the Anthropic skill’s brief-specific art direction, the Xialiang decision sheet and hard gates, a lightweight screenshot-and-interaction review loop, and a persistent token/spec file. Add searchable style catalogs or screenshot diffs only where your own evals show they improve outcomes.

## Recommended local, no-GUI toolkit (Mac, status as of 2026-09-28)

**Color palettes, contrast and color vision**
- **Adobe Leonardo** — Generates adaptive palette/theme colors from target contrast ratios. **Install:** `npm i @adobe/leonardo-contrast-colors`. **Maintenance:** mature and useful, but the npm package appears relatively quiet compared with actively releasing alternatives. **CLI or code:** Node.js library; no CLI.
- **Color.js (`colorjs.io`)** — Color-space-aware conversions and manipulation, including OKLCH; supports contrast calculations including APCA. A good general-purpose base for code that generates scales or checks colors. **Install:** `npm i colorjs.io`. **Maintenance:** active, standards-focused project. **CLI or code:** library only.
- **Culori** — Converts, interpolates and calculates color differences across CSS Color 4 spaces; useful for generating OKLCH scales and harmony variants. **Install:** `npm i culori`. **Maintenance:** established and capable; its cited npm release history is less current than the most actively updated choices here. **CLI or code:** library only. For complementary, triadic or analogous colors, rotate the OKLCH hue in a small script; these libraries are building blocks, not a universal harmony “pass/fail” checker.
- **APCA (`apca-w3`)** — Calculates the Accessible Perceptual Contrast Algorithm score. **Install:** `npm i apca-w3`. **Maintenance:** established implementation; check its current release cadence when adopting. **CLI or code:** library only. Use alongside WCAG 2.x contrast checks, not as a substitute for WCAG 2.x conformance.
- **Color-vision simulation** — The `color-blind` npm library is a small code-only option for transforming RGB colors (`npm i color-blind`); I would not treat its maintenance as established in 2026. For screenshot/image tests, a more controllable local route is to apply a chosen color-vision-deficiency matrix in a short per-pixel script, then use Sharp or ImageMagick to read/write the image. **CLI or code:** code required; no dependable top-tier, actively maintained standalone CLI surfaced here.

**Typography**
- **Capsize (`@capsizecss/core`, `@capsizecss/metrics`, `@capsizecss/unpack`)** — Uses font metrics to produce predictable text sizing and trim excess space around the baseline; metrics packages cover system/Google fonts, and `unpack` can read local font files. **Install:** `npm i @capsizecss/core @capsizecss/metrics @capsizecss/unpack`. **Maintenance:** established project; package-oriented and code-first. **CLI or code:** code, no CLI.
- **Fontkit** — Reads font metadata, glyph widths, kerning/layout features and outlines; useful for scripted checks of font metrics, glyph coverage and likely text-width differences. **Install:** `npm i fontkit`. **Maintenance:** established library; verify release cadence for a new dependency. **CLI or code:** code, no CLI.
- **Fontaine** — Creates metric-adjusted fallback font rules to reduce layout shift when web fonts load. **Install:** `npm i -D fontaine`. **Maintenance:** maintained in the UnJS ecosystem. **CLI or code:** build-time library/plugin, no standalone CLI.
- **Font pairing and type-scale checks:** There is no reliable objective package that can declare a pairing aesthetically “good.” Generate modular scales with a short script (base size × chosen ratio), use Fontkit/Capsize for metrics and line-length checks, and render the candidates for screenshot review with Playwright.

**Vector shapes and SVG**
- **Inkscape CLI** — Batch exports SVG/PDF/raster assets and can run document actions; useful for processing existing vector documents and path operations without interacting with the GUI. **Install:** `brew install --cask inkscape`. **Maintenance:** current Homebrew cask lists Inkscape 1.4.4. **CLI or code:** CLI; action support varies by operation/version.
- **Paper.js (`paper`)** — JavaScript vector scripting and path geometry, including path boolean operations; use it to generate/edit shapes in a Node workflow. **Install:** `npm i paper`. **Maintenance:** mature library; not the clearest choice if you require a fast release cadence. **CLI or code:** code, no general-purpose CLI.
- **SVGO** — Optimizes/minifies SVG files and supports configurable plugins. **Install:** `npm i -g svgo` (or add it to the project). **Maintenance:** actively releasing in 2026. **CLI or code:** both CLI and Node library.
- **VTracer** — Traces raster artwork into SVG. **Install:** npm has `@visioncortex/vtracer`; the cited Node package is an alpha, so prefer its released CLI/binary for dependable use. **Maintenance:** upstream is active, but the Node binding is marked pre-release. **CLI or code:** CLI and library options.

**Raster images and visual diffs**
- **ImageMagick** — Broad batch image toolkit for conversion, resize, crop, montage/composition, color reduction and dithering; `magick compare` reports image-difference metrics such as RMSE/PSNR. **Install:** `brew install imagemagick`. **Maintenance:** actively maintained and widely packaged. **CLI or code:** excellent CLI, also has libraries.
- **Sharp** — Fast Node/libvips library for resize, extract/crop, rotate, composite, color handling and conversion to common formats. **Install:** `npm i sharp`. **Maintenance:** actively releasing in 2026. **CLI or code:** library; write a small script, no standalone CLI.
- **pngquant** — Lossy PNG palette reduction/optimization. **Install:** `brew install pngquant`. **Maintenance:** established and available as a maintained Homebrew formula. **CLI or code:** CLI.
- **ODiff (`odiff-bin`)** — Fast native screenshot/image comparison with a visual-difference threshold and diff output; a strong local option when exact pixel equality is too brittle. **Install:** `npm i -D odiff-bin` (binary is `odiff`). **Maintenance:** actively releasing in 2026. **CLI or code:** CLI and Node API.
- **Pixelmatch** — Small image-diff library with anti-alias detection and perceptual color-difference handling; Playwright uses it for screenshot assertions. **Install:** `npm i -D pixelmatch`. **Maintenance:** actively releasing in 2026. **CLI or code:** library only.

**Layout, regression and other designer checks**
- **Playwright Test** — Captures browser/page/element screenshots and compares them with baselines; run headlessly for local layout and visual-regression checks. **Install:** `npm i -D @playwright/test`, then `npx playwright install chromium`; run with `npx playwright test`. **Maintenance:** actively maintained. **CLI or code:** CLI runner plus test code; no GUI required.
- **Style Dictionary** — Builds design tokens into platform outputs such as CSS, JavaScript, iOS and Android formats. **Install:** `npm i -D style-dictionary`; run `npx style-dictionary build`. **Maintenance:** actively maintained, with a current 5.x release in 2026. **CLI or code:** CLI and library.
- **axe-core / `@axe-core/cli`** — Automated accessibility rules for rendered web UI; run the CLI against a local page or invoke the engine in tests. **Install:** `npm i -D axe-core @axe-core/cli`. **Maintenance:** actively releasing in 2026. **CLI or code:** both; CLI uses headless Chrome. Automated checks are useful, but do not replace manual accessibility review.
- **html-validate** — Lints/validates HTML, including technical accessibility rules. **Install:** `npm i -D html-validate`; run `npx html-validate 'src/**/*.html'`. **Maintenance:** actively releasing in 2026. **CLI or code:** CLI and library.

**Practical starting set:** Homebrew: `brew install imagemagick pngquant` and `brew install --cask inkscape`. In a project, add Playwright, Sharp, SVGO, Color.js, Leonardo, Capsize, Style Dictionary and axe-core as needed. Choose the packages matching the task rather than installing every option; use local Node scripts/tests for library-only tools.
