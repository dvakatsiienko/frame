# parallel — the full surface, best practices, rivals (parallel core, 2026-09-28)

## Parallel Web Systems as of September 2026

### 1. Products and feature set

- **Search API.** Returns ranked URLs and compact, relevant excerpts for web-grounded agents. The current v1 modes are **turbo** (~200 ms, $1/1,000 requests), **fast** (~700 ms, $1/1,000), **basic** (~1 s, $5/1,000; longer excerpts), and **advanced** (~3 s, $5/1,000; deeper retrieval and compression; default). The first 10 results are included; extra results cost $1 per 1,000. In the beta-to-GA migration, beta **agentic** maps to **advanced**; beta **fast** and **one-shot** map to v1 **fast**. V1 **basic** is a distinct option for extended excerpts.
- **Extract API.** Fetches public URLs—including PDFs and JavaScript-heavy pages—and returns clean Markdown. Supply an objective to focus the excerpts on the requested information, or request full page content. It accepts up to 20 URLs per request; an objective and 2–3 varied keyword queries help focus extraction. Pricing is $1 per 1,000 URLs. Full-content extraction is not constrained by the excerpt character cap.
- **Task API.** An asynchronous web-research and enrichment service: provide an objective/input and optional task specification; it plans retrieval and returns text or schema-conforming results with a per-field research basis. Output choices include a simple text description, a text schema for a cited Markdown report, `auto` structured output, or a specified JSON schema. `pro` and `ultra` default to auto-schema behavior when no schema is supplied. Runs can be polled, completed by webhook, or streamed for progress with SSE.

| Processor | Typical use / depth | Pricing-page latency | Price per run |
|---|---|---:|---:|
| `lite` | Basic metadata, fallback; about 2 simple fields | 10–60 s | $0.005 |
| `base` | Reliable standard enrichment; about 5 fields | 15–100 s | $0.01 |
| `core` | Cross-referenced, moderately complex; about 10 fields | 60 s–5 min | $0.025 |
| `pro` | Exploratory research; about 20 fields | 2–10 min | $0.10 |
| `ultra` | Advanced, multi-source deep research; about 20 fields | 5–25 min | $0.30 |

The processor guide gives broader possible latency envelopes—e.g. `lite` 10 seconds–2 minutes, `base` 15 seconds–3 minutes, `pro` 2–10 minutes, `ultra` 3–25 minutes—and reports observed execution times separately from queue time. Treat those as workload-dependent estimates, not a guaranteed completion time. Higher-cost `core2x` and `ultra2x/4x/8x` tiers also exist. Cost is per successful Task run, not per field; failed runs are not billed.

- **Interactions and memory.** A Task response has an `interaction_id`; pass it as `previous_interaction_id` to carry context into a follow-up, including across Task processors. This interaction chain is different from long-lived Memory: memory can be personal or isolated by a `memory_scope_key`; omit the key to use personal memory where available. The key is limited to 1–128 characters and the documented pattern is letters, numbers, underscore, or hyphen. The Memory API manages memories created by Tasks, Monitors, and FindAll.
- **FindAll.** Discovers entities from a natural-language description, generates candidates, checks them against match criteria, and can enrich matches with structured fields. It supports companies, people, and other entity types; results distinguish matched from unmatched candidates. It is suited to building a dataset, rather than returning a fixed search-results list. FindAll pricing varies by generator: base is $0.25/run plus $0.03/match; core $2 plus $0.15/match; pro $10 plus $1/match; preview is $0.10 with no per-match charge. Enrichment is billed separately.
- **Monitor.** Keeps a query running on a schedule. `event_stream` monitors report new material changes; `snapshot` monitors track a Task output and report changed fields alongside the prior output. Suggested cadences are hourly for fast-moving subjects, daily for most news/signals, and weekly for slower changes. Events include citations, reasoning, and confidence. Webhooks push detected-event, successful-no-change completion, and failure notifications; alternatively, retrieve event history through the events endpoint, paginate, and filter by event group. Lite checks cost $3/1,000 executions and base checks $10/1,000.
- **Chat API and Responses API.** Chat is an OpenAI ChatCompletions-compatible beta interface supporting streaming text and JSON. Its `speed` model is low latency (about 3 seconds to first token); research models `lite`, `base`, and `core` wrap Task processors, and include research basis. The documented chat interface ignores a number of OpenAI options, so compatibility is not identical to the full OpenAI API. Separately, the OpenAI Responses-compatible **Responses API** is the documented synchronous choice for latency-sensitive web research: low/medium/high effort costs $0.01/$0.05/$0.25 per successful request, with indicative latency about 5–10/15–20/30–60 seconds.
- **MCP and CLI.** Parallel offers Search MCP (`web_search` and `web_fetch`) and Task MCP for deep research/enrichment. Search MCP can be used anonymously for free at fast mode, with optional API-key/OAuth authentication for account limits and configuration; excerpts are capped at roughly 25,000 characters per tool call. Task MCP is useful for chat clients and batch work, but its guidance recommends stronger reasoning-capable host models. `parallel-cli` exposes search, extract, research, enrichment, FindAll, and Monitor with structured JSON output. The official developer guide recommends CLI for terminal coding agents partly because CLI calls consume fewer context tokens than loading a full MCP tool catalog.
- **Default rate limits.** Search 600/min; Extract 600/min; Task 2,000/min; Chat 300/min; FindAll runs 300/hour; FindAll Entity Search 600/min; Monitor 300/min. Limits count resource-creating POSTs; status/results GETs do not count. Enterprise increases may be available.

### 2. Official best practices

- Make the research objective self-contained: state what answer is needed, relevant context, date/freshness constraints, and whether authoritative sources are preferred. For Search, use 2–3 diverse keyword queries, usually 3–6 words each; at most five are used. Put the goal in the objective and concise retrieval terms in the queries.
- For Task specs, treat each field description as the prompt for that field. Specify format, acceptable sources, timeframe, and fallback behavior (for example, return null or Unknown if evidence is unavailable). Keep inputs and schema descriptions within the documented 25,000-character combined limit. Use a real JSON schema when downstream code needs fixed keys/types; use text for reports and auto when a flexible structured result is useful.
- Choose the lowest tier that handles the reasoning complexity: `lite`/`base` for simple enrichment, `core` for reliable cross-referenced outputs, `pro`/`ultra` for exploratory or deep multi-source work. Prefer Responses for an interactive caller waiting for an answer; Task is asynchronous. Fast Task variants exist, but the processor guide does not recommend them for new workloads.
- Apply source restrictions sparingly. `include_domains` is a hard allow-list; `exclude_domains` blocks sources and applies only when include is empty. Use an objective to prefer sources when you do not need to exclude the rest of the web. Source filters can reduce coverage; up to 200 entries are allowed. Path prefixes are not supported in Search turbo. `after_date` is a Search freshness cutoff; cached content is the default, while live fetching can improve freshness at higher latency.
- Task Basis attaches URLs and excerpts, reasoning, and a confidence rating to each output field; list outputs also have per-element basis entries. Use those fields to check whether the evidence directly supports each value. Confidence is high for strong, consistent authoritative evidence; lower ratings indicate weaker, inconsistent, or limited evidence.
- Control spend with tier selection and workload design: Task charges once per successful run regardless of field count, so populate multiple useful fields in one run when appropriate. Use cheaper processors for simple steps and reserve higher tiers for difficult synthesis; account for FindAll matches/enrichment and Monitor executions separately. Search turbo/fast are the cheapest per request, but choose depth based on the task, not price alone.

### 3. Recipes, coding agents, and practical trade-offs

The official `parallel-web/parallel-cookbook` repository includes working examples such as multi-turn Search agents, fact-checking, FindAll apartment discovery, Supabase enrichment, Task Groups with Temporal, daily research feeds, vendor-intelligence monitoring, investor signals, and streamed market-analysis reports. `parallel-web/parallel-agent-skills` supplies installable coding-agent skills for search, extraction, deep research, enrichment, FindAll, and Monitor; Claude Code also has a marketplace plugin. The CLI is the practical all-API route for terminal agents, while MCP is convenient for MCP-native chat apps. For Claude Code, the documented pattern is install/authenticate the CLI and install the Parallel plugin/skills; the Search MCP can work without an account for its anonymous tier.

The main trade-off is **one unified retrieval/research surface versus specialized products**. Parallel is strongest when the unit of work is a question or structured research job: excerpts are objective-aligned, Task has schema-driven output and field-level provenance, and FindAll/Monitor extend beyond one-off search. Its downsides are asynchronous waits for Task, multiple API surfaces and processor tiers to learn, and weaker fit when the job is full-site crawling, browser interaction, or scraping at scale. In terminal agents, CLI reduces tool-schema context overhead; in MCP clients, Task MCP can still be constrained by the host model's reasoning ability and context/output window.

Comparisons should be read by workflow, not as a universal leaderboard:

- **Exa:** a better fit when semantic discovery, similar-page finding, or its contents/crawling workflow is the key need. In an independent coding-agent benchmark using search plus fetch on 100 API-documentation implementation tickets, Exa Deep scored 83.0% task completion, versus 77.0% for Parallel Advanced and 76.0% for Parallel Basic. That is a specific benchmark, not a general quality verdict.
- **Tavily:** a reasonable choice where its Search/Map/Crawl/Research workflow, familiar integrations, or simpler credit pricing fits. Parallel offers more explicit processor-tier control and a wider structured research/entity/monitoring surface, but that adds product and cost-selection complexity. Benchmark results depend on whether the test includes fetch and the model/harness used.
- **Perplexity Sonar:** Sonar is an answer/chat model with search built in; Parallel Task is a research pipeline that can be directed to a schema and returns a field-level basis. Perplexity performed strongly in the independent coding-agent test (77.3% search-only and 77.7% with its tested search/fetch setup), so it can be a good answer-first option. That benchmark evaluated Perplexity API configurations, not a definitive Sonar-vs-Task product comparison. Also, Perplexity's docs said Sonar Chat Completions would be supported until September 27, 2026, with the Agent API taking over; that lifecycle change matters as of this question's date.
- **Firecrawl:** choose it when crawling, scraping, browser interaction, or structured extraction from sites is central; choose Parallel when agent search, objective-focused extracts, or deep structured research is central. A Firecrawl-authored alternatives review flags Parallel's multi-API/tier complexity and Firecrawl's broader crawl/scrape toolkit; account for that source's vendor perspective.
- **Brave:** it represents a distinct search/index and LLM-context route. The independent coding-agent benchmark included Brave's LLM-context endpoint, but its particular ticket set and tool configuration do not establish a general ranking for all Brave use cases.
- **OpenAI deep research:** Parallel Task gives developers explicit processor selection, asynchronous runs, structured schemas, and per-field evidence; OpenAI deep research is a different managed research experience/API workflow. Parallel's own 2026 benchmark compared Task configurations with other research systems, including GPT-5.6 Sol PTC, not a clean apples-to-apples evaluation of the OpenAI Deep Research product. Treat its price/accuracy comparisons as vendor-run benchmark evidence, not proof that the workflows are interchangeable.

The independent coding-agent comparison is especially useful because it separates search-only from search-plus-fetch and reports completion, latency, and cost; its authors explicitly caution that provider choice depends on whether the agent can fetch pages. Parallel's comparison articles are useful for feature/pricing matrices but are vendor-authored. The official sources behind this summary are the Parallel documentation pages for Search Modes/migration, Extract, Task processors/pricing/best practices/Basis/interactions, Source Policy, FindAll, Monitor, Chat, MCP, CLI, and rate limits; the September 24 changelog; and the official GitHub cookbook and agent-skills repositories. Third-party references include OpenBenchmarks' coding-agent benchmark and Firecrawl's Parallel-alternatives review.
