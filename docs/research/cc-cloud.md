# cc cloud sessions — credits, setup, messaging, recipes (parallel core ×2, 2026-09-28)

## Cloud-session credits and plan usage

As of September 28, 2026, Anthropic’s launch offer is a one-time credit of **$100 for existing Pro subscribers** or **$250 for existing Max subscribers**, one per account, for **cloud sessions only**. The offer is reported as claimable through **October 7**, with unused balance expiring **November 4**. Those dates come from reporting on the offer; the official announcement confirms the amounts and cloud-session-only scope.

That promotional credit is not the same thing as either your subscription allowance or the separate paid “usage credits” used for overage. Cloud-session model requests share your account’s Claude/Claude Code rate limits; parallel work consumes those limits proportionately. Anthropic says there is **no separate compute charge for the cloud VM**. So the promotion should not be read as extra general-purpose Claude/chat/API credit, a way to raise your plan’s rate limits, or a charge for VM rental. The announcement does not spell out precisely how the promotional balance is applied against included usage or any metered overage.

**Routines** run as full Claude Code cloud sessions, and their ordinary usage draws on subscription usage. The promotion says “cloud sessions only” but does not separately specify routine triggers. The best-supported reading is that a routine run is in the eligible cloud-session category; there is no documented separate credit allowance for routines. **Subagents** are workers inside a session, not a distinct cloud-session product or credit pool: their work is subject to the parent session’s usage and lifetime. A local session exposed through **Remote Control** is different—it executes on your machine, not in a cloud environment—so it is not a cloud session.

## Start from the CLI; move work between local and cloud

- Start a new cloud task in the current repository with `claude --cloud "Fix the authentication bug in src/auth/login.ts"`. The older `--remote` spelling is a deprecated alias for `--cloud`; it is not the same as `--remote-control`.
- The cloud VM normally clones the GitHub remote at the current branch, **not your unpushed local checkout**. Commit and push first if the cloud needs local work. CLI `--cloud` supports one repository at a time. If the repository cannot be cloned through the connected GitHub access, Claude Code can upload a local bundle instead.
- Send a message to an existing cloud session with `claude -p "your message" --cloud <session-id>`; it queues the message and exits. Each `--cloud` task starts its own session, so independent tasks can run simultaneously. `/tasks` in the CLI can show progress.
- Pull a cloud session into a local checkout with `claude --teleport` (picker), `claude --teleport <session-id>`, or `/teleport` or `/tp` inside a CLI session. Teleport requires the **same repository**, a clean working tree (or stashing changes), the cloud branch to have been pushed, and the same Claude account. It fetches/checks out the branch and loads the conversation history locally. The local copy then diverges: subsequent local work does not appear in the cloud conversation. CLI handoff is one-way; it cannot push an existing local CLI session to cloud.
- There is a separate Desktop-app handoff: **Continue in → Claude Code on the Web** can send a local session to cloud, pushing its branch and carrying over a conversation summary; it requires a clean working tree and is unavailable for SSH sessions. For an ordinary local session you merely want to control from another device, use Remote Control instead; the computer and `claude` process must remain running.

## Environment, tools, network, and GitHub

Every cloud session uses a configured cloud environment. A setup script is Bash, runs before Claude Code starts as root on Ubuntu 24.04, and is for installing tools or dependencies. A nonzero exit blocks startup; keep it to roughly five minutes for environment caching. The filesystem snapshot (packages and Docker images included) is reused for later sessions and rebuilt after relevant changes or roughly seven days; running services/processes are not cached. SessionStart hooks run after Claude starts and can run on every start/resume.

Environment variables are ordinary values copied into the session at startup, and **anyone who can use that environment can read them**—do not store secrets there. On Pro and Max, API credentials can instead be stored for the agent proxy to attach to requests for specified hosts; the key does not reach Claude, commands, or the VM environment. That feature is not available on Team or Enterprise in the cited docs. It is for outbound API requests, not a way to hand a decryption key to a process.

Network access has four levels: **None**, **Trusted** (the default allowlist, including common package registries, GitHub and cloud SDK domains), **Full**, or **Custom** (your chosen domains, optionally with the defaults). GitHub uses a separate credential proxy; enabled MCP connectors and credential-host requests also use separate paths, and Claude’s Anthropic API connection remains available. A domain outside the session’s allowed route can block installs or other work.

Anthropic-hosted VMs are fresh Ubuntu 24.04 x86_64 machines with approximately **4 vCPUs, 16 GB RAM, and 30 GB disk**. The documented preinstalled tools include Python, Node.js 20/21/22, Ruby, PHP, Java, Go, Rust, C/C++ build tools, Docker, PostgreSQL, Redis, Git and `gh`; .NET is an example of a toolchain not preinstalled. **ChromeDriver is listed, but a full interactive browser is not listed in the VM inventory**—do not assume a browser is ready to use just because ChromeDriver is present. Install/configure what the task needs or use an appropriate connector. Local user settings, local tools, and interactive authentication such as AWS SSO do not carry over; commit needed project configuration or provision it in the environment.

Cloud GitHub access can be connected through the Claude GitHub App or `/web-setup`, which sends the local `gh` token to the Claude account. With `/web-setup`, sessions can reach repositories that token can access. The docs’ descriptions of App-based private-repository scope differ: the quickstart says the App must be installed on a private repo, while the cloud reference says access follows the connected GitHub account’s access and highlights App installation for PR webhooks/Auto-fix. For a private repo, make sure the chosen connection actually grants access and the repo is selected/attached. In Anthropic-hosted sessions, Git credentials stay outside the VM and are applied through a proxy; GitHub API access is scoped to repositories attached to the session.

## Limits and practical pitfalls

- **Parallelism:** the docs say cloud tasks run simultaneously in separate sessions but do not give a fixed maximum number. Capacity is provisioned on demand and rate limits are shared, so parallel tasks consume the account’s allowance faster. Routines additionally have a daily run cap; check the routines/usage page for the account’s current cap. A run starting successfully does not prove its task succeeded.
- **Duration and idle:** no fixed maximum wall-clock session length or exact idle-expiry interval is stated in the cited cloud docs. A cloud session continues when you close the browser/laptop, but stops after inactivity and its VM is reclaimed. Waiting on an MCP approval or sign-in can count as inactivity. Reopening restores the conversation in a fresh VM, **not** background shell commands or subagents that were still running. Bash commands wait two minutes by default; Claude can request up to ten minutes, after which commands can be moved to the background. This is not an assurance that the session itself stays alive indefinitely.
- **Git bundles and large repos:** local bundles must be Git repos with a commit and be under 100 MB. Larger repositories may be reduced to the current branch or a squashed working-tree snapshot and can still fail if too large. Untracked files are omitted. On macOS/Linux/WSL, uncommitted files recognized as credentials/keys (including `.env`, `*.tfvars`, `id_rsa`, and `*.pem`) are left out of the upload. A monorepo is not categorically excluded—Claude Code’s large-codebase guidance says it works with monorepos—but the VM disk/RAM limits and task scope still matter. The CLI cloud command is one-repo-at-a-time; the web quickstart supports adding multiple repositories.
- **Submodules and `git-crypt`:** I found no cloud-specific guarantee in the cited docs that submodule contents are initialized or that `git-crypt` files are unlocked automatically. A submodule is a separate repository, and GitHub proxy access is scoped to repositories attached to the session, so do not assume a private submodule will be available without access and explicit setup. For `git-crypt`, the committed encrypted data may be present, but plaintext requires the tool and a usable key in the VM. The docs do not explain a supported secure injection flow for that key; environment variables and setup scripts are readable by environment users, while proxy API credentials are deliberately hidden from commands. An unrelated reported submodule issue concerns the local `--resume` picker, not proof of a cloud-clone limitation.
- **Other friction:** cloud work does not inherit your local tools/configuration; the setup script can fail if it exits nonzero, exceeds the cache-friendly time, or needs a blocked domain. GitHub clone/push/PR workflows need suitable GitHub access. If you need local hardware, local secrets/config, a browser connected to your own signed-in tabs, or more compute than the VM ceilings, use local Claude Code/Remote Control or a self-hosted environment.

## Strong use cases and what developers should watch

The best fit is work that is well specified, independent, and does not require constant input: parallel bug fixes or PR-sized tasks (each gets its own session/branch), a repository you do not have checked out, codebase questions/exploration, and long refactors, migrations, builds or tests you want to leave running while away. Anthropic’s routine examples extend that pattern to nightly backlog grooming, alert triage, PR checklist reviews, post-deploy verification, documentation-drift PRs, and porting changes between SDKs. For a complex change, a useful pattern is to plan locally, commit/push the plan, then let a cloud session execute it.

The operational pitfalls are quota exhaustion from parallel sessions/subagents, conflicts or integration work when tasks overlap, waiting for human approval, and assuming “cloud” means permanent background execution. Keep tasks separable, ask for tests and a reviewable PR, ensure needed branches/dependencies are pushed and available, and check the transcript/diff rather than treating a green routine-run status as task success. Developer issue reports also show why overnight automation needs a fallback: one report describes a session usage limit terminating background agents and leaving a scheduled task unfired without an immediate explanation. That report concerned an interactive background-agent workflow, not evidence of a cloud-specific timeout, but it illustrates that usage limits can interrupt unattended work.

## Bottom line

Treat `claude --cloud` as a separate Claude Code session on a fresh cloud VM—not as another `claude --bg` worker on your Mac. It works from the repository’s GitHub state, has its own branch and conversation, and keeps running when your laptop is closed. Your local coordinator can communicate with it using Claude Code’s cross-session messaging, provided the sessions can see one another; the simplest supported CLI control is to queue a message to its session ID.

## 1. First-time setup that works from the terminal

**Connect GitHub and authenticate Claude.** If you want to use your existing GitHub CLI token, first run `gh auth login`. Launch Claude Code, sign in to your Claude account with `/login`, and confirm `/status` reports a Claude account rather than API-key authentication. Then, inside Claude Code—not at your shell prompt—run `/web-setup` and confirm sending the token. It stores the token encrypted with your Claude account; a self-started cloud session can access repositories that `gh` can access, without the Claude GitHub App. If your GitHub CLI is missing or unauthenticated, the command opens the browser onboarding flow instead.

Alternatively, use browser onboarding at Claude Code on the web and authorize the Claude GitHub App. For private repositories, install the App on the account or organization that owns them and grant it access to the specific repositories you want to use. This is the route to use for features that require the App, including Auto-fix and GitHub-event routine triggers. On Team and Enterprise, an Owner must enable the GitHub connector for browser sign-in; `/web-setup` is separately controlled by the **Quick web setup** setting and is off by default. Zero Data Retention organizations cannot use cloud sessions.

**Choose and configure an environment.** Pro and Max onboarding, or `/web-setup`, normally creates a `Default` environment. Team and Enterprise onboarding may ask you to create it. `Trusted` is a practical starting network level: it permits the documented allowlist of common package registries and other domains, not unrestricted internet. Use `Custom` to allow additional hosts, `Full` for unrestricted access, or `None` when the session needs no outbound network. In Claude Code on the web’s environment selector, add a Bash setup script for system tools or dependencies; from the CLI, `/remote-env` selects the default environment for future cloud sessions.

Setup scripts run as root on Ubuntu 24.04 before Claude starts. Keep them reliably under roughly five minutes and make them exit successfully: a failing script blocks session startup, and an overlong script may prevent environment caching. `Trusted` covers many package registries, but not every arbitrary download host; use `Custom` or `Full` when a required install source is blocked. The setup script runs when the environment cache needs rebuilding, not on every resumed session.

**Keep secrets out of ordinary environment variables.** On Pro and Max, an organization admin can add API credentials to an existing Anthropic-hosted cloud environment. Configure the credential’s allowed host and request header; Anthropic’s proxy attaches the secret after the request leaves the VM, so Claude and commands in the session do not see the key. This is for calls to external services—not a way to authenticate the Claude model session with an API key. GitHub access uses a separate GitHub proxy. API credentials are not currently available in the environment dialog on Team or Enterprise; values stored as normal environment variables are readable by anyone using that environment.

**Start with a deliberate Git state.** From the repo, push the branch and commits you want the VM to use, then run:

```bash
git status
claude --cloud "Fix the authentication bug in src/auth/login.ts; run the relevant tests and report what changed"
```

For a GitHub repo the Claude GitHub App can access, the cloud VM clones the remote at the current branch; it does not magically include local unpushed commits. When Claude Code bundles a local repository instead, tracked working-tree changes can be included, but untracked files are not. Check the CLI’s upload summary, especially for credentials. Bundling has size and repository requirements, and does not make a non-GitHub remote pushable.

**Common first-attempt failures and fixes**

- **API-key sign-in, third-party model provider, or `Unable to get organization UUID`:** cloud sessions require a Claude-account login. Run `/login` and retry. A third-party provider such as Bedrock or Vertex is not supported for `--cloud`; a plain API-key login is not a substitute.
- **`/web-setup` is unknown or missing:** run it inside an interactive Claude Code session, not in your shell. Sign in with `/login`; on Team/Enterprise ask an Owner to enable Quick web setup. If that is unavailable, connect GitHub through the browser flow. ZDR also disables this feature.
- **No repository appears or cloning is denied:** check that the browser-installed App is installed on the repository’s owning account/organization and that the repository is selected, or verify the `gh` account with `gh repo view OWNER/REPO` and rerun `/web-setup` after changing GitHub accounts. A missing `workflow` scope can make pushes that edit Actions workflow files fail; refresh it with `gh auth refresh -s workflow` and reconnect.
- **No cloud environment / environment creation failure:** use `/web-setup` or create an environment in the web environment selector; update the CLI if it predates automatic environment creation. On Team/Enterprise, ask an Owner about organization access or policy.
- **Setup script fails or hangs:** inspect it with `set -x`; fix paths and commands for a fresh Ubuntu clone, ensure the required hosts are reachable under the network policy, and make noncritical commands tolerant of failure (`|| true`). Break up or parallelize installs that exceed the cache-build time budget.
- **Provisioning fails before setup:** check Claude service status and retry after a short wait; capacity allocation can fail temporarily. An organization IP allowlist can also block Anthropic-hosted sessions because the API calls originate from Anthropic infrastructure; ask about an exemption or use a self-hosted environment.

## 2. Local-to-cloud communication, visibility, and stopping

**Send a message to an existing cloud session:**

```bash
claude -p "Add a regression test, run it, and send me the result" --cloud <session-id>
```

The session ID can be the bare ID or a Claude Code on the web session URL. The command queues one message and exits; it does **not** wait for the cloud session’s answer. `--output-format json` provides a machine-readable send result. This works from another machine logged into the same Claude account and sends no local working-tree state. Use a task description with `claude --cloud` to create a new session; use `-p` plus an ID to message an existing one.

**Use `SendMessage` for agent-to-agent coordination.** Cross-session messaging is different from passing text with the CLI: Claude discovers peers with `ListAgents` and sends messages with `SendMessage`. Your local coordinator can ask to list its peers and message the cloud worker; `/list-agents` is the CLI command for inspecting reachable peers. Cloud sessions can participate in cross-session messaging. Importantly, the local coordinator must be connected to Remote Control to discover cloud sessions in its peer list. Remote Control keeps execution and files on your Mac; it is not cloud execution. Keep the receiving session reachable and check its inbound-message settings. Permission checks still apply, and messages do not transfer conversation history or files.

A cloud session can send a message back through `SendMessage` when it has a reply route to the target session. Do not rely on the special `notify_when_idle` subscription for a cloud worker: that one-notice idle subscription is documented for sessions on the same machine, not cross-machine/cloud peers. For dependable completion reporting, tell the worker to message the coordinator when done, or have it post a result through a connector or to its PR.

**Read progress and transcript.** The session list and live conversation are available in Claude Code on the web. `claude --teleport` opens a cloud-session picker; `claude --teleport <session-id>` brings a pushed cloud branch and the full conversation history into a local terminal. Teleport creates a local copy: subsequent local work does not sync back to the cloud conversation. It requires the same account, the correct repository, a clean working tree (or accepting the stash prompt), and a branch pushed to the remote. `/list-agents` is useful for reachable-agent status, not a general transcript reader.

There is no documented general-purpose individual-user CLI/API for polling a cloud transcript or stopping a cloud VM. Do not confuse the Compliance API’s remote-session endpoints with a Claude Code cloud-session transcript API: Anthropic’s Compliance FAQ says Claude Code cloud sessions are not captured by that API. Compliance endpoints are an enterprise compliance feature, not a substitute for the web session transcript.

**Stop or notify.** `claude stop <id>` is for local background sessions, not cloud sessions. The documented cloud-session controls are the web session UI (including archiving or deleting a session) and sending the worker an instruction to stop and summarize. Cloud VMs are reclaimed after inactivity; background commands or subagents still running when reclamation occurs are not restored. Routine API triggers start runs, but they are not completion webhooks. If you need a callback, a repo-committed hook can make an HTTP request from a cloud session; hooks run in cloud sessions too. Use a `Stop` hook with care because it fires when Claude finishes responding to a turn, not only when the entire job is permanently complete. A worker message, PR, or explicit external-service report is often simpler.

## 3. Useful workflows and operating practices

- **Parallel PR work:** launch separate `claude --cloud` tasks for independent changes. Each gets its own branch/session. Give each a narrow scope and avoid overlapping files or shared migrations; separate branches prevent simultaneous edits from overwriting one another, but they do not eliminate merge conflicts when PRs are integrated. Review each diff and test before merging. Cloud and local agents draw on shared account usage, so parallel workers burn limits faster.
- **Plan locally, execute in the cloud:** use `claude --permission-mode plan` on the Mac to explore and agree on a plan without edits. Save the plan in the repository, commit and push it, then start `claude --cloud "Execute docs/migration-plan.md"`. This avoids asking the VM to act on a plan it cannot see.
- **Overnight jobs:** choose a self-contained task with explicit success criteria and a request to test, push, and summarize or open a PR. Ensure setup finishes promptly and dependencies are cached. Avoid a task that will sit awaiting your approval or an MCP sign-in; inactivity can lead to VM reclamation, and unfinished background work is not resumed. For recurring unattended work, use Routines rather than leaving an interactive session to wait indefinitely.
- **Routines and schedules:** create one with `/schedule` or in Claude Code on the web. Routines run as full cloud sessions and support schedules (hourly, daily, weekdays, weekly, or one-off), GitHub events, and API-triggered runs. A deployment pipeline can call a routine’s authenticated API trigger after deploy and pass smoke-test context; the routine can check the deployed build/logs and report a go/no-go via a connector. The trigger’s `text` is untrusted payload, so the saved prompt must explicitly tell Claude how to use it. GitHub-event routines require the Claude GitHub App; `/web-setup` alone does not enable webhook delivery. Routines consume subscription usage and have a daily run cap.
- **Code review:** for a PR, a GitHub-triggered routine can apply a repeatable review checklist and post findings. Auto-fix can watch CI failures and reviewer comments and push clear fixes, but it requires the GitHub App. GitHub does not send an event when the base branch advances and creates a merge conflict, so ask Claude to rebase/resolve those conflicts explicitly. Review bot-authored comments and repository automation carefully before enabling comment-triggered actions.
- **Research and exploration:** cloud sessions are useful for repository questions, tracing behavior, and independent exploration without a local checkout. They start from repository content, not your Mac’s user settings, installed tools, local MCP configuration, or uncommitted/untracked files unless those are deliberately carried in a bundle. Commit reusable instructions, skills, and agents to the repo if cloud workers need them.
- **Managed coordination:** if you want Anthropic’s cloud coordinator rather than the Mac session to divide and track work, Projects are the separate managed option: one ongoing conversation coordinates parallel cloud threads. That is not the same as turning an existing local session into a cloud session; CLI handoff is one-way via teleport.

## 4. Usage and remaining balance

Cloud sessions consume the same account subscription rate limits as other Claude/Claude Code usage; parallel sessions consume limits proportionately. Anthropic says the hosted VM has no separate compute charge. A September 2026 Anthropic developer announcement also offered existing subscribers one-time cloud-session trial credits of **$100 for Pro** and **$250 for Max**. Keep that promotional balance distinct from the normal plan quota.

For ordinary Pro/Max usage, Claude Code’s status-line input can expose `rate_limits.five_hour` and `rate_limits.seven_day` used percentages and reset timestamps after the first API response. A local status line can show remaining percentage as `100 - used_percentage`; it is not a balance for an individual cloud session or the promotional credit. The routine page/usage settings show routine daily-run consumption, but the documented status-line schema has no cloud-session-credit balance field. I found no documented CLI or API to retrieve the remaining promotional cloud-session credit programmatically; check the account’s usage interface for balances rather than treating the status line as a credit ledger.

## 5. Headless browser in a cloud session

A cloud VM is a fresh Ubuntu 24.04 x86_64 machine, not your Mac with its Chrome profile or GUI. For local headless testing, put Playwright in the repository’s dependencies and install its Chromium browser and system dependencies from the cloud environment setup script (for example, Playwright’s Chromium install with OS dependencies). Make sure the install/download domains are reachable, keep setup within the caching time budget, and have the task run the tests headlessly. The environment documentation lists `chromedriver` among preinstalled tools but does not promise a ready-to-use Chromium browser; verify the actual browser installation in a session. The local `--chrome` integration is not a way to drive your Mac’s browser from the cloud VM.

For interactive browsing or to avoid downloading and maintaining a browser in each environment, use a remote browser service such as Browserbase through its hosted MCP service or its official Claude Code browser skills/CLI. That moves browser execution to the remote service and gives the cloud agent browser tools; it also introduces a third-party service and its credential/network requirements. If connected as a Claude.ai MCP connector, connector traffic is routed through Anthropic rather than the session’s network allowlist. If you configure a remote MCP server directly in the repository instead, ensure the session can reach its host and protect its credentials. In short: install Playwright/Chromium when you need reproducible local-to-VM E2E tests; use Browserbase when you want a managed remote browser and are comfortable with that external dependency.
