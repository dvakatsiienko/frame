## 1. which roles mature setups run

finding: the same small set of roles shows up everywhere. a searcher/explorer, a planner or architect, a read-only reviewer, a debugger, a verifier that checks findings, and, at Anthropic, a separate cleanup/simplifier. the big public collections add many domain specialists. the solid sources don't treat those specialists as the core.

- claude code ships three built-ins: Explore ("search or understand a codebase without making changes"), Plan ("codebase research for planning") and general-purpose ("both exploration and modification, complex reasoning … or multiple dependent steps"). source: https://code.claude.com/docs/en/sub-agents (built-in subagents)
- the same doc's example cards are code-reviewer (read-only: "tools: Read, Grep, Glob, Bash"), debugger, data-scientist and db-reader. its best practice is "each subagent should excel at one specific task". source: https://code.claude.com/docs/en/sub-agents (example subagents)
- anthropic's feature-dev plugin has three roles: code-explorer, code-architect and code-reviewer, all `model: sonnet`. its command launches "3 code-reviewer agents in parallel with different focuses: simplicity/DRY/elegance, bugs/functional correctness, project conventions/abstractions". source: https://github.com/anthropics/claude-code/tree/main/plugins/feature-dev (agents/*.md, commands/feature-dev.md:106)
- anthropic's pr-review-toolkit has six narrow reviewers: code-reviewer, code-simplifier, comment-analyzer, pr-test-analyzer, silent-failure-hunter and type-design-analyzer. source: https://github.com/anthropics/claude-code/tree/main/plugins/pr-review-toolkit/agents
- anthropic's research system uses a lead agent, parallel search subagents and a CitationAgent that "process[es] the documents and research report to identify specific locations for citations". source: https://www.anthropic.com/engineering/multi-agent-research-system
- obra/superpowers (about 297k stars) runs implementer subagents, one task reviewer per task "(spec compliance + code quality)", and "a broad whole-branch review at the end". source: https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md (line 8)
- framework docs use the same split. openai agents sdk offers "agents as tools" vs "handoffs", and an evaluator loop: "run an evaluator agent to assess that output … stop when the evaluator says the output passes". source: https://openai.github.io/openai-agents-python/multi_agent/. anthropic names "orchestrator-workers" and "evaluator-optimizer". source: https://www.anthropic.com/engineering/building-effective-agents
- the collections are broad, not deep. VoltAgent has 100+ cards in 10 categories, 18 of them under quality-security (https://github.com/VoltAgent/awesome-claude-code-subagents). wshobson/agents has "202 agents" (https://github.com/wshobson/agents README). both are catalogs to pick from, not a working roster.
- where sources disagree: cognition argues against parallel subagents that write. "running multiple agents in collaboration only results in fragile systems". it accepts subagents that only answer "a well-defined question". source: https://cognition.ai/blog/dont-build-multi-agents. langchain lands in between: "multi-agent systems that primarily 'read' are easier than those that 'write'". source: https://blog.langchain.com/how-and-when-to-build-multi-agent-systems/. all six of our cards read except helper, so we sit on the safe side of that line.

## 2. what our six miss, what overlaps

finding: no role is missing outright. explore, review, research, extraction and mechanical edits are all covered. the coordinator does planning, so we don't need a plan or architect card. the real gaps are two jobs inside review: checking against the intent, and verifying findings. there is one soft overlap, helper vs sifter.

- **gap, intent check.** checkup reads only what the caller hands it: "The brief names the sweep (what changed, why, which files …)" (checkup.md:9). nothing tells it to open the wish itself. anthropic's version reviews "the rate limiter diff against PLAN.md. Check that every requirement is implemented … and nothing outside the task's scope changed". source: https://code.claude.com/docs/en/best-practices (add an adversarial review step)
- **gap, finding verification.** anthropic's code-review command runs one extra subagent per finding "to validate that the stated issue is truly an issue", then "Filter out any issues that were not validated" (https://github.com/anthropics/claude-code/blob/main/plugins/code-review/commands/code-review.md:55-57). managed Code Review has "a verification step [that] checks candidates against actual code behavior" (https://code.claude.com/docs/en/code-review). checkup has no such pass. its own gate step (checkup.md:16) only covers the exit-code part.
- **not a gap, debugger and security.** the docs show a debugger card. but the same docs say to stay in the main conversation when "the task needs frequent back-and-forth or iterative refinement" (https://code.claude.com/docs/en/sub-agents, choose between subagents and main conversation), and debugging is that kind of job. security is covered by the bundled `/security-review` (https://code.claude.com/docs/en/commands).
- **overlap, helper vs sifter.** both produce "a report read off a script's output" (helper.md:3) or "counts, fields and lines out of big files" (sifter.md:3). helper also edits, sifter doesn't. superpowers measured cheap models "routinely take 2-3× the turns on multi-step work" (SKILL.md:208-210). so the split that holds up is: single-command extraction goes to sifter (haiku), and a multi-step script report goes to helper (sonnet). keep both cards. sharpen the descriptions rather than merging.
- **no overlap, Explore vs sifter vs researcher.** Explore finds code (explore.md:3), sifter reads logs and transcripts, researcher reads outside sources with `omitClaudeMd` (researcher.md:6). the docs warn that descriptions must "single out one subagent" (https://code.claude.com/docs/en/sub-agents, best practices). ours already do.
- **no overlap, retro vs checkup.** retro reads finished transcripts and fixes the environment (retro.md:3). checkup reads a diff mid-session. different inputs, different timing.

## 3. how a review subagent is best shaped

finding: give it the diff plus the verbatim intent, but no extra repo context. keep it read-only and give it no Agent tool. cap the output and require file:line evidence for each finding. size the model to the risk, with sonnet as the floor and opus for subtle changes. the evidence that intent-aware review catches more defects is suggestive, not proven.

- **what it reads, intent.** anthropic's command tells every review agent "the PR title and description. This will help provide context regarding the author's intent" (code-review.md:53). superpowers gives its reviewer three paths: "the same brief file, the report file, and the review package" (SKILL.md:325-326). it also notes the limit of a paraphrased brief: "it cannot catch requirements dropped during the controller's extraction from the plan" (https://github.com/obra/superpowers/blob/main/docs/superpowers/specs/2026-06-09-sdd-task-scoped-review-dispatch-design.md:154). that argues for handing checkup the wish file itself, not the coordinator's summary.
- **what it reads, code context.** the anthropic bug agent should "Focus only on the diff itself without reading extra context" (code-review.md:36). superpowers' spec reviewers, told "Only read files in this diff", "stayed tight: 6-16 tool calls". quality reviewers without that rule "ran repo-wide greps" and cost "4-8× what spec reviewers cost" (dispatch spec:7-10).
- **evidence on intent, preprints only.** ContextCRBench (8 LLMs) finds "textual context yields greater performance gains than code context alone" (https://arxiv.org/abs/2511.07017). SWE-PRBench finds models "detect only 15-31% of human-flagged issues" diff-only, and that all 8 "degrade monotonically" as file and repo context is added. "a structured 2,000-token diff-with-summary prompt outperforms a 2,500-token full-context prompt" (https://arxiv.org/abs/2603.26130). read together: intent text helps, extra code hurts. i found no controlled study that varies only the wish text against diff-only and measures real defects. whether an intent-aware checkup catches more real defects in our setting stays «?».
- **where sources disagree on context.** anthropic's best practices say a fresh reviewer "sees only the diff and the criteria you give it". its managed Code Review examines changes "in the context of your full codebase" (https://code.claude.com/docs/en/best-practices vs https://code.claude.com/docs/en/code-review). the preprints lean toward the first.
- **output cap.** anthropic's toolkit reviewer: "Only report issues with confidence ≥ 80" (pr-review-toolkit/agents/code-reviewer.md:32). Code Review suggests "Report at most five Nits per review", and after the first round "post Important findings only" (code-review docs, REVIEW.md section). `/code-review` has `--max-findings` with a default limit (commands doc). checkup's "≤10 lines … severity ordered high → low" (checkup.md:19) fits this pattern.
- **over-reporting.** "A reviewer prompted to find gaps will usually report some, even when the work is sound … Chasing every finding leads to over-engineering. … flag only gaps that affect correctness or the stated requirements" (https://code.claude.com/docs/en/best-practices, callout). checkup lets "clean" count as a valid result (checkup.md:19), which is good. it doesn't yet say "requirements only".
- **evidence per finding.** superpowers added an evidence rule after "reviewers passing defects the prompt had pointed them at … got unsupported 'yes' answers" (dispatch spec:132). Code Review suggests "behavior claims need a `file:line` citation in the source, not an inference from naming". checkup's line format already asks for `file:line` (checkup.md:19).
- **model tier.** anthropic's toolkit reviewer and simplifier are `model: opus`. feature-dev's reviewer is `model: sonnet`. wshobson puts "code review" under Opus (docs/agents.md). superpowers says to "choose the model … scaled to the diff's size, complexity, and risk", to "use a mid-tier model as the floor for reviewers", and that "scoped re-reviews of small fix diffs take a cheap-to-mid tier" (SKILL.md:196-211). checkup on opus fits a pass over a large batch. a sonnet re-check after a small fix is supported too.
- **no nesting.** superpowers: "Never spawn a subagent to review part of the diff … a reviewer you spawn duplicates one of them at full cost" (requesting-code-review/code-reviewer.md:54-61). the claude code docs say to omit `Agent` from a reviewer's `tools` so it can't spawn (sub-agents doc). checkup's `tools: Read, Grep, Glob, Bash` (checkup.md:6) already does this.

## 4. cost and context

finding: a subagent saves the caller's context when it reads a lot and returns little. it costs more in total tokens, has a fixed spin-up cost, and starts on a cold cache. it loses when the job needs the caller's context or repeated back-and-forth.

- **saves the caller:** "Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)". source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **costs overall:** "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats". source: https://www.anthropic.com/engineering/multi-agent-research-system
- **cold cache:** a subagent's "first request doesn't read the parent's cache, because the two prefixes differ". a fork "inherits the parent's system prompt, tools, and conversation history exactly, so its first request reads the parent's cache". source: https://code.claude.com/docs/en/prompt-caching. the sub-agents doc adds "a fork costs less than a fresh subagent for tasks that need the same context".
- **spin-up and latency:** "A subagent that isn't a fork starts fresh and may need time to gather context". source: https://code.claude.com/docs/en/sub-agents
- **measured per-dispatch overhead:** superpowers' profiling blamed "per-dispatch overhead (3 subagent spin-ups per task, each re-deriving the diff; controller coordination was half the dollars)". merging two reviewers into one went to "47.5 min / 15.7M / $13.55 — beat baseline on every axis". the final config was "-32% time, -37% tokens, -27% dollars vs baseline". same-config reruns varied from "44.4→57.1 min" (dispatch spec:36-75). one dispatch "hit 42k chars of which 99% was pasted history" (SKILL.md:268-270).
- **cheap is not always cheaper:** "678 of 1197 subagent turns were haiku", and cheap models take "2-3× the turns on multi-step work — costing more overall" (dispatch spec:42-44, SKILL.md:208-210). an omitted model "inherits your session's model … which silently defeats" model choice. one session inherited opus "for 17 dispatches, +$5". all our cards pin `model:`.
- **description budget:** descriptions sit in every session's context. there is a warning past "15,000 tokens" (sub-agents doc). our six are far below that «?» (not measured, but each description is one paragraph).
- **price of a full review:** managed Code Review "averages $15-25 in cost" per review (https://code.claude.com/docs/en/code-review). that sets the bar a 10-line opus checkup is competing with.

## 5. failure modes

- **duplicated work and vague briefs:** "Without detailed task descriptions, agents duplicate work, leave gaps … one subagent explored the 2021 automotive chip crisis while 2 others duplicated work" (multi-agent research post). each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" (same post). our researcher card requires the brief to carry "the question, the vectors, the output shape and path" (researcher.md:3).
- **vague termination and overinvestment:** early agents were "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources", and "continuing when they already had sufficient results". the fix was effort rules: "Simple fact-finding requires just 1 agent with 3-10 tool calls" (multi-agent research post). our caps: checkup "stop at ten lines" (checkup.md:11), sifter "a reply over ~40 lines means the question needs a sharper filter" (sifter.md:14). helper, retro and researcher have no stop rule beyond the brief.
- **trusting the report:** "Treat the implementer's report as unverified claims … 'left it per YAGNI' … is the implementer grading their own work" (https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/task-reviewer-prompt.md:64-71). anthropic: "Have Claude show evidence rather than asserting success" (best practices). helper already says "The caller checks your diff" (helper.md:16). sifter returns "the command or commands that produced it, so the caller can re-run them" (sifter.md:19). checkup's findings have no verify step on the caller side (see 2).
- **prompt injection through reports:** "Claude Code scans each subagent's final report before Claude reads it … text from those sources can carry instructions aimed at the main conversation" (sub-agents doc). this matters for researcher and sifter, which read outside text.
- **role overlap and duplicate seats:** "every reviewer a worker spawned duplicated the task review the controller dispatched anyway — a full extra review seat per task" (SKILL.md:274-276). "The quality template's 'Plan alignment' dimension re-checks what the spec reviewer just verified" (dispatch spec:17). this is the risk of running a checkup and a separate intent reviewer side by side.
- **conflicting implicit decisions:** "Actions carry implicit decisions, and conflicting decisions carry bad results" (cognition). this applies to any card that edits in parallel. only helper edits.
- **lost state after compaction:** "real sessions re-dispatched entire completed task sequences after compaction — 269 dispatches for ~22 tasks" (dispatch spec:92-93).
- **taxonomy:** MAST groups 14 failure modes from "1600+ annotated traces" into "(i) system design issues, (ii) inter-agent misalignment, and (iii) task verification" (https://arxiv.org/abs/2503.13657). i read only the abstract. the per-mode rates are «?».

## 6. separate cleaner next to the reviewer, or one role

finding: Anthropic keeps them as two separate jobs, and the cleaner runs after review passes. other sources fold cleanup into review. for us the evidence favors no separate card: run the bundled `/simplify` after checkup, or add a cleanup line to checkup. a separate sonnet "cleaner/optimizer" card would duplicate a bundled skill and add a dispatch.

- **split, anthropic product:** "`/simplify` … Four review agents run in parallel, covering reuse of existing helpers, simplification, efficiency, and whether the change is at the right level of abstraction. The review doesn't look for correctness bugs. Use `/code-review` to find bugs" (https://code.claude.com/docs/en/commands). history: "The command was named `/simplify` before v2.1.147 … `/simplify` runs a separate cleanup-only review that applies fixes without hunting for bugs" (code-review docs). so anthropic once had a single command and split it.
- **split, anthropic plugin:** the toolkit's workflow is "Review passes → **code-simplifier** (polish)" and "After Passing Review: code-simplifier" (pr-review-toolkit/README.md). the simplifier edits code ("Never change what the code does - only how it does it", code-simplifier.md:42) and is `model: opus` (line 35), not a cheap tier.
- **folded:** feature-dev makes "simplicity/DRY/elegance" one of three reviewer focuses (feature-dev.md:106). `/code-review` "Depending on your model and effort level … also covers reuse, simplification, and efficiency cleanups" (code-review docs). superpowers names "verbatim duplication, swallowed errors, assertion-free tests" as Important inside the one task reviewer (dispatch spec, iteration 3).
- **cost of a separate seat:** superpowers' biggest cost cut came from merging two reviewers into "one reviewer, one reading of the diff, two verdicts" (dispatch spec:54-58).
- **risk of a cleaner:** the over-reporting warning in 3 applies twice over. a subagent asked to simplify will find something to simplify. anthropic's own simplifier card spends a whole section on "Avoid over-simplification" (code-simplifier.md:63-70).
- **where sources disagree:** anthropic's pr-review-toolkit and bundled skills keep two roles. feature-dev, `/code-review` at higher effort, and superpowers keep one. no source measures defects or tokens for "split vs merged cleanup" specifically «?».
- **sonnet for cleanup:** feature-dev runs its simplicity reviewer on sonnet, and superpowers sets "a mid-tier model as the floor for reviewers". both support sonnet if a cleaner ever exists. which model the bundled `/simplify` agents use is not documented «?».

## proposed roster

- **helper: keep.** mechanical edits need a sonnet worker with the coder's guides (helper.md:13). narrow its description to edits and multi-step script reports, and send single-command counts to sifter.
- **researcher: keep.** a bounded source question with `omitClaudeMd` is the "well-defined question" case even cognition accepts.
- **retro: keep.** a different input (finished transcripts) and a different output (environment fixes). nothing else does this.
- **sifter: keep.** the docs' top use case is keeping verbose output out of the caller. limit it to one-command extractions, because haiku takes 2-3× the turns on multi-step work.
- **Explore: keep.** it overrides the built-in onto sonnet, which the docs explicitly allow ("keeps its own `model` field").
- **checkup: keep and widen, merging in the proposed intent role.** add three things. (a) the brief passes the wish's path and checkup reads it verbatim (a paraphrase hides dropped requirements). (b) checkup gives two verdicts in the same ≤10 lines: intent (missing, out of scope, loose ends) and quality. (c) "flag only what breaks correctness or the wish". one reader of the diff instead of two seats, as in superpowers' cheapest config. consider moving it from cclio to `~/.claude/agents/` so coder sessions can use it too «?» (whether coders need it on top of verifier sessions is dima's call).
- **intent/drift reviewer as a separate card: drop.** it would re-read the same diff as checkup. that is the duplicate seat superpowers measured and removed.
- **cleaner/optimizer card: don't add.** the bundled `/simplify` already covers reuse, simplification, efficiency and abstraction level, run after review passes. if a card is ever wanted, use sonnet, read-only, and propose rather than apply.
- **finding verification: add as a step, not a card.** the coordinator or caller checks each high checkup finding against the cited `file:line` before acting, as anthropic's code-review command does per finding. no new agent.
