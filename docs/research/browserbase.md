# browserbase — cloud browsers for agents (parallel core, 2026-09-28)

# Browserbase deep dive — as of 2026-09-28

## Bottom line for your setup

Browserbase is cloud browser infrastructure; it does not replace the Claude Code session running on your Mac or in Claude Code’s cloud environment. Your agent can drive a Browserbase-hosted browser through the REST API/SDK and CDP, the Browse CLI, Stagehand, Browserbase’s hosted MCP server, or Vercel’s `agent-browser` provider. For local Mac development and remote Claude Code alike, the hosted MCP endpoint or `browse` CLI is the quickest smoke test. Use Playwright/CDP or Stagehand when you want reproducible, code-owned behavior; use Browserbase Agents when you want Browserbase to own the autonomous web-task loop.

**CLI naming caveat:** the official CLI ecosystem has a naming transition. Older Functions material shows `bb` commands, and `@browserbasehq/cli` is presented as an official CLI package; the current unified CLI documentation calls the command `browse` and documents `npm install -g browse`. Don’t assume `bb` and `browse` are interchangeable binaries: check the installed CLI’s help and use the current `browse` docs for its cloud, browser, Functions, and skills workflows.

## Features: what they do, limits, and how you drive them

| Feature | What it does and how it is driven | Limits / practical notes |
|---|---|---|
| **Browser sessions and Live View** | A session is an isolated cloud browser. Create it with the Sessions REST API or Node/Python SDK, then connect over CDP with Playwright, Puppeteer, Selenium, or Stagehand. Live View provides a real-time window for watching, clicking, typing, scrolling, and human-in-the-loop work. Get Live View URLs through the session debug API; they can also be embedded read-only or read/write. | Free: 3 concurrent sessions, 15 minutes maximum per session, and 5 session creations/minute. New sessions must be connected within 5 minutes. Paid keep-alive sessions can survive disconnects; the maximum session duration is 6 hours. A CDP connection with no commands for 10 minutes can be closed. |
| **Human login / 2FA handoff** | **Yes, practically:** open the active session’s interactive Live View, let a person enter credentials or complete 2FA, then let the waiting automation continue on that same session. Browserbase explicitly supports human-in-the-loop and authentication handling. | This is interactive control of a live browser, not a guarantee that every autonomous run will pause itself and resume correctly. Arrange a checkpoint/wait in your script or agent, keep the session alive, and confirm the automation is still attached before continuing. A completed or timed-out session cannot be handed back. Avoid placing real credentials in prompts or logs. |
| **Contexts** | Persist a Chromium user-data directory across sessions: cookies, localStorage, IndexedDB, sessionStorage, service workers, autofill data, and browser preferences. Create a Context through the Contexts API and pass its ID when creating a session; set `persist: true` to save changes when the session closes. This is useful for login once, then reuse the authenticated state. | Contexts persist indefinitely until deleted or invalidated; website cookies/tokens can still expire. The stored Context is uniquely encrypted at rest. The ordinary HTTP asset cache is not persisted. Wait a few seconds after closing a persistent session before reusing it; avoid concurrent sessions mutating the same Context. Docs recommend one Context per site/login and do not state a hard Context-count or size cap. Context retention is distinct from session artifact retention. |
| **Recording, replay, logs** | Session video/replay is enabled by default. Inspect sessions in the dashboard, or retrieve per-tab HLS replay playlists through the API and download recordings as MP4. The Session Inspector also exposes activity, network, console, and performance information. Disable recording with `recordSession: false` when you do not want a replay. | Replay docs say ordinary non-BYOS recording sources are retained up to 31 days, while the Free plan’s account data-retention row says 7 days. For Free, plan on the stricter 7-day window and export anything important promptly; the published retention statements are not fully aligned. Signed HLS segment URLs last 6 hours; request a fresh playlist to play later. |
| **Functions / Runtime** | Deploy TypeScript browser scripts or agents to Browserbase infrastructure. The function gets a Browserbase session for its invocation and can return JSON. Develop locally, publish with the CLI, then invoke via HTTP; production invocations are asynchronous and can be polled. Build/invocation webhooks are available. The docs even show a Claude Agent SDK example controlling the invocation’s browser through Playwright MCP. | Functions are free on every plan, but the docs list a 15-minute maximum execution, TypeScript only, no persistent storage between invocations, no private npm packages, and availability only in `us-west-2`. Secrets management is described as not yet available in the referenced docs; don’t pass sensitive credentials casually as invocation parameters. Functions documentation describes API invocation and webhooks, not a built-in cron scheduler. Director separately advertises scheduling. |
| **Agents and runs** | A managed autonomous agent takes a natural-language task and can use browser controls, Search/Fetch, files, and shell, then return structured output. Create reusable agents with a system prompt/result schema, or create an agent and first run together. Drive it through the Agents API/SDK; runs are asynchronous, poll status and messages, and inspect the associated session Live View/replay. | Free includes 3 Agent calls. Runs have `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `STOPPED`, and `TIMED_OUT` states. Agents may skip the browser if Search/Fetch is enough. Current docs say the built-in tools cannot yet be added to or disabled, and run integration is poll-based; run webhooks are described as planned. Agents are outside ZDR/BYOS scope in the cited docs. |
| **Director** | A separate no/low-code product: describe a task, watch and correct a browser agent, export the resulting Stagehand code, and deploy the workflow. Its page advertises one-off runs, daily/weekly schedules or triggers, and scaling across sessions; it also describes manual approvals and 1Password integration for sensitive steps. | Useful for prototyping a workflow before owning the code. Do not confuse Director’s advertised schedules with a general cron facility in Browserbase Functions. The public product page says free to try, but does not establish that Director usage is covered by the Browserbase Free plan’s quotas. |
| **Search API** | `POST /v1/search` or SDK/CLI: web discovery returning result titles, URLs, and optional metadata. A useful flow is Search → Fetch → browser session only when interaction is needed. | Free includes 1,000 Search calls; plan rate is 2/sec (120/min). A query can return up to 25 results. |
| **Fetch API** | Fetch a URL without starting a full interactive browser. Return raw content, Markdown, or schema-shaped JSON; optionally use Browserbase proxies/geolocation. REST API or SDK. | Free includes 1,000 Fetch calls. It does not execute JavaScript, has a 5 MB content limit and 60-second timeout, and does not convert PDFs to Markdown/JSON. Use a real browser for dynamic, authenticated, large, or interactive pages. Fetch proxying supports Browserbase-managed proxy configuration, not custom proxy routing. Markdown/JSON extraction is a separately priced Fetch Extract operation. |
| **Model Gateway** | Stagehand can use Browserbase’s API key to route to model providers instead of requiring separate provider keys. The cited docs list OpenAI, Anthropic, and Google examples; model selection is configuration, and Stagehand can choose a model if one is omitted. | Requires a Browserbase-hosted browser; it does not work with local browsers. Model tokens are billed at the provider’s market price, with no stated markup. This is not a general-purpose Claude Code model proxy; it is documented as a Stagehand integration. |
| **Extensions** | Upload a zipped Chrome extension through the SDK/API/CLI, then create sessions with its extension ID. | ZIP must have `manifest.json` at its root and be no larger than 100 MB. Starting a session with an extension can take longer because the browser has to restart/load it. |
| **Uploads and downloads** | For uploads, Playwright can use a local file path from the machine running the automation; for remote/manual Live View upload, upload the file through the Session Uploads API and attach it to the file input. For downloads, configure the remote browser download behavior, then retrieve/list/delete files through the Downloads API. | Live View’s native file picker cannot see files on your Mac. Manual upload needs a local picker plus API/CDP handling. Downloads sync to Browserbase storage and are retrievable by API; Playwright/Puppeteer need the documented CDP `downloadPath: 'downloads'` configuration. Screenshots/PDFs are generally returned to your code rather than stored like downloaded files. The cited upload guide does not give a universal upload-size ceiling. |
| **Verified / identity and CAPTCHA** | Agent Identity includes Verified browser profiles, CAPTCHA handling, auth support, and Web Bot Auth for participating sites. Verified uses complete fingerprint profiles; the guide lists desktop OS profiles plus mobile/tablet choices. Live View can help with human authentication. | Verified is Scale-plan-only in the plan/docs. Free’s plan matrix says Verified: No and CAPTCHA: No; Developer/Startup list Basic Verified and automatic CAPTCHA. A separate CAPTCHA guide says solving is enabled by default for sessions, so treat the plan matrix as the Free-plan constraint and do not count on free CAPTCHA solving. Supported CAPTCHA solving may take 5–30 seconds and is not universal. |
| **Proxies** | Browserbase-managed residential proxies, country/state/city geolocation, custom HTTP/HTTPS proxies, and domain-based routing are configured at session creation. Fetch supports simpler managed proxy routing. | Free has 0 GB and cannot use proxies in the plan table; Developer and above can. Geolocation is best-effort. Provider restrictions make banking, government, streaming, ticketing, webmail, and some other targets unreliable or unavailable. Proxy traffic is separately metered; the plan docs specify a 1 MB minimum per proxy session. |
| **Mobile / devices** | Regular sessions can set a viewport and use normal browser automation/emulation. Verified offers fixed, fingerprint-matched desktop/mobile/tablet profiles. Live View can show a mobile viewport. | This is browser/device-profile and viewport emulation, not evidence of a fleet of native iOS/Android devices. Verified viewports are fixed and cannot be customized. Mobile Live View keyboards are not officially supported; a client may need to build a virtual keyboard and forward key events. |

## Free plan, exactly

The Free plan is **$0**, no credit card, with **1 browser hour/month**, **3 concurrent browsers**, a **15-minute maximum session**, **5 session creations/minute**, and **7-day data retention**. It also lists **3 Agent calls**, **1,000 Search calls**, and **1,000 Fetch calls**. The browser-hour allowance is time, not a fixed number of sessions: short and long sessions consume it differently. Browser time is billed by the minute with a one-minute minimum per session, so a task finishing in seconds can still use a billed minute. The Free plan lists **0 GB proxies**, **no Verified**, and **no CAPTCHA**. Functions are stated to be free on every plan. Do not interpret the 1-hour allowance as one hour for each agent or each concurrent browser.

## Strengths, weaknesses, and comparisons

**Strongest fit:** very low setup burden; standard CDP compatibility with Playwright/Puppeteer/Selenium; reusable encrypted login Contexts; practical human takeover; unusually useful session replay/network/log debugging; and a coherent set of session, file, Search/Fetch, Stagehand, Functions, MCP, and managed-Agent options. The Browserbase-specific value is more than “a remote Chrome”: it is the managed lifecycle, observability, and human/agent handoff around it.

**Weak spots to test:** a fully managed service gives less infrastructure control than self-hosting; Free is a small evaluation budget and excludes the strongest proxy/identity features; one-minute billing can be inefficient for many tiny jobs; protected sites remain site/provider-dependent; and high-level Agents trade deterministic code control for autonomy. Functions have meaningful beta-era limits (region, runtime, language, storage/secrets). Free-plan retention and CAPTCHA wording should be treated conservatively as described above.

**Real-user signal:** public first-hand feedback is sparse and anecdotal rather than a dependable benchmark. Reddit discussions mention cost at scale, the one-minute minimum, and occasional flakiness on JavaScript-heavy single-page apps. Treat those as useful failure modes to test—not measured platform-wide rates. A GitHub alternatives discussion gives subjective impressions (Browserbase stability, Steel cost transparency, Kernel performance/innovation, Browserless stealth); it is not a controlled comparison.

| Alternative | Practical comparison |
|---|---|
| **Browserless** | Its own comparison emphasizes self-hosting/hybrid deployments, more browser engines, REST/BrowserQL options, and proxy control; Browserbase’s appeal is the managed, agent-oriented session/observability stack. If you need self-hosting or Firefox/WebKit, Browserless deserves a direct test. The comparison is vendor-authored. |
| **Steel** | Open-source/self-hosting and a published lifecycle benchmark are its main comparison points. Steel’s own article says Steel is faster on its published lifecycle benchmark and invites users to rerun the harness; measure in your target region and workload rather than taking that as a general result. |
| **Kernel** | The located direct comparison is a community GitHub discussion, not a benchmark. Its qualitative shorthand favors Kernel for performance/innovation and Browserbase for stability; validate with your own concurrency, reconnect, and target-site tests. |
| **Browser Use Cloud** | Browser Use is an open-source agent framework with a hosted Cloud product that handles managed browsers, memory, proxy rotation, and stealth. It is a more agent/product-oriented alternative; Browserbase offers lower-level browser infrastructure plus Stagehand and its own managed Agents. Compare agent success/cost on the same tasks, not just browser-hour prices. |
| **Hyperbrowser** | A Browserless-authored comparison reports Hyperbrowser connected faster while Browserbase opened pages slightly quicker in its test. This is a narrow reported benchmark, not a general latency ranking. |
| **Anchor** | Anchor is another managed browser option, with comparison material covering pricing, stealth, and compliance. The available comparison evidence is not enough to claim a universal performance winner; include it if auth-heavy/headful behavior or its deployment model matters to you. |

## What I would stress-test in one Free-plan week

1. **Set up both local and cloud-agent access first.** From the Mac, try `browse` with a remote Browserbase session and the hosted MCP server from Claude Code. Repeat from Claude Code’s cloud environment using the same Browserbase project key stored as a secret. Compare setup friction, session creation, reattachment, and whether Live View is usable from both. Keep the key out of committed MCP URLs/config files.
2. **Spend the most time on one real login workflow.** Use an account you are authorized to automate. Create a Context, log in manually through Live View, complete a 2FA checkpoint, close with persistence enabled, wait briefly, and start another session with the same Context. Confirm cookies and localStorage survive; also test what happens after logout/token expiry. This is the most distinctive high-value workflow for your Claude Code use case.
3. **Test replay and recovery, not just a happy path.** Run a 5–10 minute Playwright/Stagehand job, watch it live, inspect network/console output and replay, then intentionally cause a navigation/selector failure. Test disconnect/reconnect only if your plan supports keep-alive; confirm how a non-keep-alive session ends.
4. **Use Search/Fetch before burning browser time.** Try a stable static page, a JavaScript-heavy page, a PDF, and one URL that needs interaction. Compare raw versus Markdown/JSON Fetch, test the 5 MB/timeout behavior safely, then escalate only the cases Fetch cannot handle to a browser session.
5. **Try files and one extension.** Download a small PDF/CSV and retrieve it through the API; upload a local test file through Playwright and manually through the Live View flow. If extensions matter to your real tasks, upload a tiny test ZIP and measure startup overhead.
6. **Use the three included Agent calls deliberately.** Try one public research task, one structured extraction task, and one multi-step task with a human checkpoint. Inspect run messages, final schema, session replay, and per-run duration/cost. Compare the same task to your own Claude Code + Playwright/Stagehand script.
7. **Track the one-hour budget and stop before the cap.** Record creation time, active browser minutes, run outcomes, whether a session unexpectedly persists, and which workflow needed retries. Free cannot fairly test proxy geolocation, Verified identity, or dependable CAPTCHA solving; those are paid/Scale evaluations, not meaningful Free-plan pass/fail tests.

**Decision rule:** if the week proves that Claude Code can reuse login state, ask for human help in a live browser, and recover/debug failed runs without you managing Chromium infrastructure, Browserbase is a strong fit. If your essential target requires Verified/proxies, sustained sessions, high-volume tiny jobs, native device testing, or self-hosting, the Free-plan test cannot settle the decision; those are the specific paid-plan or alternative-provider tests to prioritize.
