# jev / typesafe — features, question practice, the skill-suggestion recipe (parallel core, 2026-09-28)

## TypeSafe AI / System One, as of 28 September 2026

### 1. Product, features and API

TypeSafe describes System One as a decision model for software workflows: send application state and typed questions; receive constrained answers and probabilities, not generated explanations, code, or replies. Jev does not itself use tools or take workflow actions; your application combines its answers and controls routing and side effects. Its input is text only, including strings and JSON objects or arrays of text—not images, audio, or video.

The official API has three primitives, not five:
- **Noul**: a yes/no judgment, returning the probability of yes from 0 to 1. It has no separate confidence field.
- **Choice**: select one option from a closed set; returns the chosen option, a probability for every option, and confidence. Up to 255 options are allowed.
- **Score**: rate one dimension along ordered levels; returns a probability-weighted score, the distribution across levels, and confidence. Criteria require at least two and allow up to ten levels.

So **enum/choice is native; boolean is Noul; ranking and extraction are workflows built from the primitives and code, not separate question types**. For ranking, score candidates or ask one Noul per candidate and sort the results. For extraction, generate candidate spans with code or another model, then ask Jev to choose or verify; code handles exact parsing and normalization. Scores can also be normalized and combined with explicit weights in code.

The HTTP endpoint is `POST /v1/systemone`, with `state`, `model`, and a `questions` map. Each question has an ID, type and instructions; Choice and Score have criteria, and Noul may define what true and false mean. IDs are for your application and do not affect inference. A request can mix types and ask multiple questions against the same state. Answers are returned under their IDs, with model version and token usage. The API also offers `GET /v1/models`; errors include validation, authentication, rate-limit and overload responses.

Current listed Jev is **1.13**, version **`jev-1.13.0`**. `jev-latest` resolves to that stable release; aliases may move, so pin a version if thresholds depend on it, and record the model returned in the response. The documented context limits are **64k tokens for state plus all questions**, and **32k for state plus the longest question**. As listed, limits are **250,000 tokens/second and 1,200 requests/minute**, but TypeSafe says limits can change dynamically; higher limits are available on custom/enterprise plans. Pricing is **$42 per billion input tokens ($0.042 per million)**; output tokens are free.

The official product pages describe most queries as completing in about 100 ms; the launch post gives **70–500 ms end-to-end**. Published cookbook measurements report roughly 111–114 ms for particular calls, while real round trips vary with state size, network and hosting. TypeSafe’s official clients include Python and JavaScript/TypeScript (`@typesafe-ai/sdk`; Node 20+); typed answers are inferred in TypeScript. There is also a direct HTTP API and integrations/gateway support.

### 2. Question-writing, state and evaluation practices

Ask for one narrow judgment at a time—the kind a knowledgeable person can make quickly. Keep instructions short and specific; the docs do **not** prescribe a numeric word/character limit. Start with strings. Use structured instructions or criteria when you need named context, examples, boundaries, or data supplied by code. For structured state, use descriptive JSON fields, point questions to the relevant field with a backticked path, and keep content/evidence in `state` separate from the question. Include only relevant context: the model’s 32k state-plus-longest-question limit is not a recommendation to fill that budget, and unrelated detail can reduce accuracy.

For a **Choice**, include the complete plausible option set and add `other`/`none` when appropriate. Define options so the boundaries are clear. When labels are easy to confuse, describe what each covers, what it is *not* for, and a few representative examples, using parallel fields across labels. For a **Score**, use concrete descriptions of situations at each level—not bare numbers, vague adjectives, or descriptions that depend on neighboring levels. Keep one dimension per Score; split multiple considerations and combine normalized scores in code. Use as many distinct levels as you can explain, up to ten. For Noul, ask one yes/no proposition, phrase it so high means yes, and define true/false when the boundary needs clarification. These structured examples are rubric guidance, rather than a requirement to write a long few-shot prompt. Examples should resemble real inputs; test whether they actually help.

Questions in one request are evaluated independently and in parallel. Batch questions that share state—including speculative questions whose answers may be ignored in some code paths. The official 13-question cookbook reports identical answers under batched and separate calls in its test, with the large-document example **12.2× cheaper and 10× faster** when batched than 13 sequential calls. Truly dependent stages need separate calls, such as fetch-more-evidence workflows. Where possible, keep deterministic arithmetic, date comparisons, counting, exact parsing, thresholds and side effects in code.

Choice/Score `confidence` summarizes how concentrated the returned probability distribution is; it is **not** the probability that the answer is correct. Noul’s value is itself P(yes). Calibration is a different property: across groups of predictions, probabilities should correspond to observed frequencies; it is not a guarantee for an individual answer. Use the full distribution as well as the summary confidence. Pick thresholds using labeled data and the cost of a wrong action: act on low-stakes, high-confidence routes; ask for confirmation or review on ambiguous or high-stakes ones; abstain or fall back when appropriate. A cutoff such as 0.5 or 0.9 is an example, not a universal setting.

For evaluation, keep representative labeled examples and test the exact question/criteria on them; inspect errors and revise definitions, then check revised criteria against separate examples. Plot confidence against accuracy to set thresholds. The docs do not prescribe a universal fixture size or a full benchmark protocol. Their self-consistency cookbooks repeat questions 15 times and track label/probability variation, which can reveal instability but does **not** establish accuracy. A practical external recommendation is to label 50–100 items and record probabilities, latency and cost; calibrate thresholds on your own domain. Pin model versions while comparing prompt variants, then retest when changing model versions or aliases.

### 3. Cookbooks and routing many options

The official cookbook catalog includes: **Self-consistency: nouls; Self-consistency: choices; Parallel questions; Re-ranking; Line-by-line search; Structure recovery; Function calling; Skill suggestion; Knowledge graph entity alignment; Classifying RAG passages; Double-checking citations; Guardrails for LLMs; SDE cascade; Date extraction; Pre-parsed value extraction; Hierarchical classification; Autoresearch feature discovery;** and **Classification using confidence**. The examples cover routing, ranking, verification, classification, extraction and multi-stage pipelines. A Smart Home Assistant demo is also published.

For a roster of around 50 tools or skills, one Choice can represent the options (within the 255-option limit). Write the question around the user’s *intent*, and define each option by its capability and boundaries—not just a short name or a matching keyword. The official skill-selection recipe demonstrates a more robust pattern on **182 skills**: first Choice-rank the whole roster using short index descriptions, while separate Noul questions determine whether the request needs a skill at all; then re-check the top three against fuller descriptions and instruction excerpts, with permission to suggest none. It distinguishes “what subject is this about?” from “does this request require a skill/action?”—an explanation request can be about the same subject as a skill without needing that skill.

The recipe’s failure analysis is especially useful: truncated one-line descriptions made two PowerPoint skills look alike, so the first rank picked the wrong one; fuller descriptions in the second pass corrected the author-versus-editor choice. But a two-stage shortlist cannot recover a correct option omitted from the shortlist, and a close-but-wrong skill can survive verification (their Mastodon example selected an X/Twitter skill). In its 488-request test, the suggestion reduced wrong skill loads from 16.8% to 7.3% and needless loads from 9.8% to 4.0%, but some previously correct agent choices became wrong. The practical fix is richer contrastive descriptions, an explicit “none applies” gate, fuller evidence for close candidates, confidence/fit thresholds and a human or larger-model fallback for consequential ambiguity. For more than 255 options, chunk/rank and re-check candidates or use a hierarchy; greedy tree traversal can lock in an early mistake, while the hierarchy cookbook’s beam search retains multiple paths.

The docs do not describe a universal “surface-word matching” bug as a Jev-specific rule. They do warn that Jev can be literal: unclear scope, negation, indirect references, adversarial content, contradictions, and irrelevant context can all produce errors. Their prescription is to state exact conditions, point to relevant fields, contrast confusing options, test edge cases, and compose atomic answers in code. Do not expect it to count reliably, do arithmetic, infer unstated values, or generate text.

### 4. Developer reports and comparisons

The evidence supports Jev as a potentially fast and inexpensive **bounded decision layer**, not an automatic accuracy upgrade or a replacement for generative/reasoning models. TypeSafe’s launch claims comparable capability on System One tasks with much higher speed and lower cost, but its own evaluation discussion notes that reference-model comparisons are not ground-truth accuracy labels and that some workflows were authored by its team. Treat vendor claims and benchmark setups accordingly.

Independent results are mixed by task and methodology. One 791-decision benchmark reports that confidence gating improved accuracy on its 8-way and 77-way tasks at reduced coverage; a Jev-first cascade sometimes approached a frontier model at lower cost, while the author cautions that Jev can still be confidently wrong when labels overlap. A separate 3,080-example Banking77 report says Jev beat Qwen by 4.7 percentage points in that test, but found that replacing low-confidence Jev answers with Qwen introduced more errors than it fixed. LiteLLM reports Jev at 95.00% versus Haiku at 73.75% on 80 synthetic, authored cases and 5.43× faster median classification latency; LiteLLM explicitly cautions that the expected tiers were authored and need independent held-out evaluation. A 40-call, four-tier model-routing experiment reported perfect matches for its straightforward examples and about 0.64–0.67 seconds round-trip, but explicitly says it is not a comprehensive accuracy test or an integrated-router latency result.

Early developer/community reports are similarly encouraging but not definitive. A Reddit user reports 94% agreement on 10,000 labeled search-intent queries and a much faster/cheaper batch run, while noting misses on Hinglish rent/PG queries and unfamiliar locality names; this is a user report, not a controlled benchmark. Another agent-router post describes only two successful examples and correctly notes that a constrained output can still be the wrong option. A developer who tested roughly 100 coding tasks describes using separate coordination, uncertainty and consequence judgments, then routing by thresholds, while calling the results preliminary. Community feedback also stresses measuring wrong-but-confident decisions, abstentions, fallbacks and accuracy—not latency alone. Hacker News discussion questions whether comparing against generated structured outputs is a fair speed comparison and whether model-consensus reference labels are ground truth.

On embeddings, the public recipes found are **hybrid**, not a direct Jev-versus-embedding-router benchmark: use BM25 or embeddings to retrieve a manageable candidate set, then use Jev to judge relevance, classify passages or rerank. The TypeSafe reranking cookbook reports improved top-1/top-10 retrieval accuracy on its legal-query dataset, but that result compares its reranking pipeline with its baseline, not Jev against an embedding router in isolation. No conclusion that Jev universally beats embeddings follows; the useful comparison is on your own labeled traffic, with the same candidates, metrics, thresholds and fallback policy.
