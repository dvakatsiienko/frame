# mods — cc function-hook plugins, one per folder, each its own plugin

the x marketplace lists x-mod-stash, the one worth sharing; x-mod-guard, x-mod-redact and x-mod-holds stay local, run from source only (dima, 2026-10-08).

## the doors

- a mod runs from source: `CLAUDE_CODE_PLUGIN_DIRS` in `~/.claude/settings.json` `env` names each mod folder (plus `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` for desktop-born sessions), so a save reloads it at the end of the turn, no bump, no `/reload-plugins`; the installed `<mod>@x` stays disabled. a new mod joins that list. proof: `claude -p --debug-file <f> ok` prints `hooks module <mod>@inline loaded`; the env reaches only sessions started after the edit
- every edit of a live mod goes through `x mods edit` (FRM-388): `pull <paths…>` prints scratch copies, `Edit`/`Write` those, `test` validates and tests the mod on an overlay copy (`--against HEAD` runs the edited tests on HEAD's mod, «errored» apart from «failed»), `push` writes them only when that overlay is green, all files or none, restoring from a backup on a failed write; an unpulled file is refused («was never pulled», nothing written) and lands only with `--add`, and a pulled file the repo changed since is refused too (pull it again). biome run on a scratch copy outside the repo panics (exit 101, «path is expected to be under the root»): feed it on stdin, `pnpm exec biome format --stdin-file-path=<the repo path> < <scratch file>`. a save under `hooks/` reloads into every session at its next turn end, so x-mod-guard refuses a direct edit there while the mod's test is red, and a bg session's isolation guard blocks one anyway (no per-path exemption, only `bgIsolation: none`)
- tests run through `claude plugin test`, never vitest: `pnpm mods:test [<mod>…]` runs every mod (or the named ones), prints only the failing tests' output, `--extra <file>` adds one outside test file to the one mod named, and ends with one line, `mods:test: 4 mods green, <n> pass, 0 fail` or `red in <mod>` (`<mod> (<file> did not load)` for a test file that cannot load); it and `x mods edit test` read the output alike, both held to `plugin-test.sample.txt`. it also reds a clock read in a mod's `hooks/` outside the `$.clock` fallback; a sync path names itself with `// clock-ok: <why>` on the line above. the scripts beside the mods (`test.ts`, `live.ts`, `*.test.ts` there) are vitest's. `pnpm mods:typecheck` runs tsc over those scripts (`mods/tsconfig.json`), then each mod against its engine-written types; a commit touching `mods/` runs both (lefthook `mods`)
  - 📌 `x mods edit test` and `push` run no tsc: run `pnpm mods:typecheck` after a push and before the commit (two commits died at the hook on a green overlay, 2026-10-12)
  - the authoring docs are [cc's mods docs](https://code.claude.com/docs/en/plugins/mods/overview), the bundled `plugin-authoring` skill (it says write a mod under `~/.claude/dev-mods/<session>/`; here a mod lives in `plugin-x/mods/<mod>`, and local wins) and the per-build types; this folder holds only what they miss
- a new x-mod-guard hint or rule runs `pnpm mods:replay [days]` before it ships: the last days' real Bash calls from every transcript, each hint's fire count and three samples, so a false fire shows before the fleet meets it
- a mod test is proven red with `red-proof --cmd <file> <anchor> <replacement> -- claude plugin test home/.claude/plugin-x/mods/<mod>` (plugin bin; `--pairs` for many lines), never a hand swap
- `pnpm mods:live <mod dir>` is the reload and hover check for every mod round, what `claude plugin test` cannot reach (FRM-322): a real cc session in a pty with the dev copy swapped into the child's `CLAUDE_CODE_PLUGIN_DIRS` (as `mods:probe` does), named `mods-live: <mod>` on the board, run in the background
  - wait for `mods:live ready: <mod>` before the first keystroke, never a fixed sleep; each save then prints `reload ok: <the engine's load line>`, `reload ok: no hook changed, still loaded` (the save left `hooks/` and the manifest as they were) or the error (a name clash reads «another plugin of that name loads first»), and writes a text frame to `$TMPDIR/mods-live/<mod>/latest.txt`
  - the load lines come from the session's `--debug-file`, never the screen: cc draws on the alternate screen, which keeps no scrollback
  - its verbs: `hover <label>`, `click <label>`, `type <text>` (with Enter: a prompt or a `/board`), `fill <text>` (a draft) — each prints the frame once the screen quiets — `status` (the server pid, the cc pid and the session holding the slot, exit 0; free, exit 1); the desktop look stays dima's eye
  - stop it with `kill $(cat $TMPDIR/mods-live/<mod>/server.pid)`
- `pnpm mods:probe <mod dir> "<prompt>"` runs one headless session with a dev copy in place of the live mod of the same name and exits 1 unless the engine read the dev copy (FRM-392); the swap rides the child's process env, since a `--settings` env swap loads the live copy
- a mod outside `CLAUDE_CODE_PLUGIN_DIRS` is probed live with `claude -p "<prompt>" --plugin-dir <mod> --allowedTools=Bash`, run with `run_in_background` (x-mod-guard refuses a foreground `claude -p`, FRM-395; `# fg-ok: <why>` for a real need); an env var on the command line loses to the one in `settings.json`, and `--allowedTools` without `=` eats the prompt

## the rules

- a new refusing or injecting hook ships warn-only until its verifier says clean: mods load from main, so a commit reaches every session at its next turn end (FRM-392). in x-mod-guard a new rule joins `WARN_ONLY` in `hooks/register.ts` (the call runs, the model gets «would refuse», the event is kept as `warned`) and leaves it on the clean; `rule-mode:<rule>` = «enforce» in its store turns a listed rule on early, and nothing in the store can make a rule warn, since every session writes that store (dima's o70). the warn path is proven by red-proof listing a rule
- a probe's consuming hook (one that holds, swallows or rewrites a delivery) unloads the turn its proof lands: its folder leaves `--plugin-dir` and `~/.claude/dev-mods/` (pk-93's `qc-view` swallowed cclio's 16:03 brief after its proof passed)
- a mod initialises on `session.start`, never `classic.SessionStart`: a hot reload fires only the first
- a mod hooks only events every live engine knows: an engine refuses the whole module over one event it lacks, so `pnpm mods:skew` (in the commit gate) checks each mod against every version a live session runs and against the cc the desktop app bundles (read from `Claude.app`'s `app.asar`, `X_CLAUDE_APP` names another path), and exits non-zero when a mod needs a newer engine than the desktop's; a new event waits until no session runs an engine without it
- a mod's manifest `name` stays its folder's (`names.test.ts`): a loaded mod renamed keeps its old identity and every `$.state` call is refused; a rename moves `~/.claude/plugins/store/<old>_*` to the new name and restarts every session
- every tree-returning `ui.render` hook passes its tree through `cleanTree` (`x-mod-stash/hooks/tree.ts`) inside a try/catch: one control character refuses the whole tree, and a throw draws a one-line notice instead of a blank (claude-code#91870)
- who a session is comes from the registry's name (x-mod-stash's `isLaneOwner`) or `$.session.root()`, never `$.session.cwd()`, which follows a Bash `cd`; compare names through `bare()`. `$.session.id()` changes at `/clear` and `/resume` with no `session.start`: refresh a kept id from `session.end` or the next `command.run`
- fleet state starts at the registry: `~/.claude/sessions/<pid>.json` carries `status` (busy · shell · idle · waiting · blocked · needs_input), `statusUpdatedAt`, `hostSessionId`, `bridgeSessionId` for every session; read it before writing any state of your own (FRM-306)
- a `$`-using helper is a top-level function in `register.tsx`: the validator follows `$` only into top-level functions of the same file, never across an import and never into a closure `$` is handed to. an import reaches only files inside the mod's own folder (a path outside it, or a symlink inside it, fails validate), so two mods share code by copy or through a store file; each copy sits between `// twin <name> — …` and `// twin end`, and `twins.test.ts` fails when two copies differ (FRM-400)
- every interactive element names itself on hover (dima, 2026-10-05); the hover traps are `engine.md`'s
- a visual dima is asked to judge gets a way to see it on demand, built before the ask: a look that shows only under a condition (mid-turn, a spinner, an error) gets a switch or a preview that holds it on while idle — «how do you expect me to test it if it happens only under certain conditions?» (dima's o6, 2026-10-11; stash's `/board breathe` keeps the bars breathing idle). a layout change on the board shows a `mods:live` frame or a mock ask before its commit
- a 🎛️ settings switch is the whole feature, for every mod and every part a future mod adds: off = nothing drawn, nothing in any model's context, no turn spent, its tool op refused in one line naming the switch; on = all of it back. a new part ships with its row in the switch-gate test (dima, 2026-10-13: «any mod that toggles always fully disables if toggled off»)
- a mod's `Link` takes only `https:` (or `http://localhost`): a `linear://` href is drawn as plain text; opening an app needs a `Button` running `open <url>` through `$.process.run` (FRM-382)

## where the rest lives

- `engine.md` — what the engine does, probed: lifetimes, budgets, rewrite semantics, cross-session marks, drawing and hover, the test-harness traps; read its section when a probe or a test bites
- `workarounds.md` — every mods want the engine can't do yet: the want, the upstream issue, the workaround, the undo; a coder who hits a new engine gap adds its entry in the same commit as the workaround (dima, 2026-10-10); `refresh-cc-mods` re-checks it each run
- `api-map.md` — every hook event by name, and the fleet ideas; at a cc bump diff its list against `EngineEventOf`
- `<mod>/FTR.md` + `<mod>/GLOSSARY.md` — read your section before changing what x-mod-stash, x-mod-redact, x-mod-guard or x-mod-holds does
